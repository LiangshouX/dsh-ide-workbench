# 代码智能（补全 + Usage / 跳转定义）性能开销评估

> 状态：**实测评估稿**（2026-10-31）— 配套文档：`docs/代码智能-可行性评估.md`
> 评估问题：引入全量 LSP 后，插件本身、DSH 宿主、以及用户机器的性能开销有多大？DSH 会不会变卡？
> 测量环境：i5-10300H（**4 核 / 8 线程**）、**15.8 GB 内存**（测量时空闲 3.7–5.5 GB）、Windows 11、Node v22.22.2
> 语言服务器：`typescript-language-server@6.0.2` + `typescript@5.9.3`（npm 实装）

---

## 0. 结论

**会多占资源。默认不会让 DSH "卡"，但有一个此前被低估的真实风险：语言服务器在大项目上会吃掉 GB 级内存，甚至 OOM 崩溃，把整台机器拖进换页。**

| 维度 | 结论 | 实测 |
|---|---|---|
| **内存** | ⚠️ **这是真正的风险点**，不是 CPU。语言服务器稳态可达 **1.6–2.2 GB**（800–3,000 文件规模）；在 3,120 文件的"中心依赖"型项目上冲到 **4.2 GB 后 OOM 崩溃**（exit 134） | 见 §1.1 |
| **CPU** | ✅ 空闲时**不烧核**；只有建 program 与查询时吃一个核 | 见 §1.3 |
| **DSH 宿主卡顿** | ⚠️ 唯一真实通道是**宿主主线程被大 JSON 同步解析阻塞**。朴素实现漂移 **412 ms**；worker_thread 隔离后 **8 ms** | 见 §1.4 |
| **浏览器端** | ✅ 客户端产物 +363 KB（+15%），运行时开销可忽略 | 见 §1.5 |

**必须做的三件事**（否则"装了之后反而更卡"是必然的用户反馈）：

1. **给语言服务器设死内存上限**（`maxTsServerMemory`）—— 不设的话 tsserver 会一路涨到 4 GB 再把机器拖垮（实测）。
2. **把 LSP 客户端放进 Node `worker_thread`** —— 宿主主线程零阻塞（DSH 自己已有两个 worker_thread 先例）。
3. **空闲自动退出 + 崩溃自动恢复** —— 不用代码时把进程杀掉省内存；崩溃后要能重启并给出明确提示，而不是静默失效。

**额外工程量：约 2 人天**，把 LSP 主线从 11–15 人天变成 **13–17 人天**。我认为这笔必须付。

## 1. 实测数据

### 1.1 语言服务器内存（⚠️ 最重要的一组）

> **测量更正**：最初用 `tasklist` 只测到了 `typescript-language-server` 这个**包装进程**（45–61 MB）。真正的 `tsserver` 是它的**孙进程**，用 CIM 采样整棵进程树才测到真实值。下表是更正后的数据。

| 项目形态 | 文件数 / 体积 | 语言服务器进程树峰值 RSS | 结果 |
|---|---|---|---|
| 小项目（本插件自身，无 tsconfig） | 54 源文件 | **~60–100 MB** | ✅ 正常 |
| 对抗型 A：中心依赖 + `strict` | 800 文件 / 22.4 MB | **1,783 MB**（稳定不涨） | ✅ 存活 |
| 对抗型 B：浅依赖 + 非 strict | 3,000 文件 / 31.5 MB | **2,202 MB**（稳定不涨） | ✅ 存活 |
| 对抗型 C：中心依赖 + `strict` | 3,120 文件 / 81.6 MB | **4,431 MB** | ❌ **OOM 崩溃（exit 134 / SIGABRT）** |

崩溃时的进程树：

```
node#17008 = 4,225 MB   ← tsserver（被 OOM 杀死）
node#22368 =   103 MB   ← typescript-language-server 包装进程
node#1628  =    58 MB
```

**结论**：tsserver 的内存主要随 **符号总量 / 类型图规模** 增长，几千个文件、几十万个符号 → GB 级。这与 VS Code 在大型 TS 项目上 tsserver 吃掉 1–4 GB 的社区共识一致，不是本项目的特殊问题。

⚠️ **在没有内存上限的情况下，这台 15.8 GB 的机器（测量时空闲仅 3.7–5.5 GB）会被直接拖进换页，用户感知就是"整机卡"**，而不是"DSH 卡"。这是本评估最重要的一条。

### 1.2 请求延迟与载荷（小项目，54 源文件）

| 请求 | 延迟 | 载荷 | 结果 |
|---|---|---|---|
| `initialize` | **419 ms** | 1.6 KB | 能力齐全（completion / definition / references / symbols） |
| `textDocument/completion` | **84 ms** | 73 KB | 1000 项 |
| `textDocument/definition` | **12 ms** | 0.2 KB | |
| `textDocument/references` | **209 ms** | 16.7 KB | 98 处命中 |
| `workspace/symbol` | **196 ms** | 216 KB | 1027 项 |

### 1.3 CPU

| 场景 | 实测 |
|---|---|
| 语言服务器**空闲**（无请求） | **不烧核**。建完 program 后 RSS 稳定在 1.78 GB / 2.17 GB 不再增长，CPU 无明显占用 |
| 建立 program（打开文件后） | 吃满一个核数秒到数十秒；本机只有 4 个物理核，会和 DSH 的 agent 工具调用抢 CPU |
| 宿主进程（DSH Host） | LSP 管理器本身是 I/O 等待型，CPU 占用可忽略 |

> **测量更正**：先前的"空闲 0.00 s / 10 s = 0%"是 `wmic` 的 CPU 列在现代 Windows 上返回空值导致的**假零**，不可作为证据。已改用 CIM 的 `KernelModeTime + UserModeTime`（100 ns 单位）重新测量：**20 秒空闲期内，语言服务器进程树合计消耗 0.00 s CPU（0.0% 单核），RSS 变化 −1 MB**。结论成立，且现在是可信的。

### 1.4 宿主进程（DSH Host）开销 —— "卡顿"的唯一真实通道

DSH Host 是承载插件 HTTP API、终端 WebSocket、git 轮询的 Node 进程。宿主每 2 秒轮询一次 `git status`（`store.js:1083` + `host/git.js:269`）。

| 载荷 | 主线程 JSON.parse | 只做字节中继（不解析） | 比值 |
|---|---|---|---|
| 增量 didChange（典型，13 KB） | 0.33 ms | 0.03 ms | 11× |
| **全文 didChange @ 插件 1 MB 上限** | **37.9 ms** | **1.5 ms** | **25×** |
| completion（实测 270 KB） | 5.9 ms | 0.25 ms | 24× |
| workspace/symbol（实测 814 KB） | 13.7 ms | 1.3 ms | 11× |
| 超大 monorepo 引用（8.9 MB） | **188.7 ms** | **7.8 ms** | **24×** |

**宿主事件循环漂移**（25 ms 采样探针）：

| 实现方式 | p50 | p95 | p99 | max | >50 ms 次数 |
|---|---|---|---|---|---|
| 朴素实现（主线程解析 + WS 中继，18 MB 载荷） | 15.0 ms | 412 ms | 412 ms | **412 ms** | 3 |
| **worker_thread 隔离** | 7.0 ms | 8.0 ms | 8.0 ms | **8 ms** | **0** |

宿主被阻塞时，受影响的是：终端输出渲染延迟、git 状态刷新延迟、其它插件 API 调用延迟。**不影响** DSH 的对话/模型请求（走网络 I/O），但"终端打字延迟""文件树刷新慢"是能感知的。

### 1.5 浏览器端

| 项 | 实测 |
|---|---|
| `@codemirror/lsp-client@6.3.0` + `marked@15.0.12` 打包后 | **363 KB（minified）** |
| 插件 `dist/client.js` 当前 | 2,413 KB（实测 `2471316` bytes，基线 commit `dd6dc17`） |
| → 客户端产物增长 | **+15%**（→ ~2.78 MB），一次性下载/解析成本 |
| 运行时内存 | 可忽略 |
| ⚠️ 默认请求超时 | **3000 ms**（`@codemirror/lsp-client/dist/index.js:547`：`config.timeout ?? 3000`） |

## 2. 逐层回答"会不会让 DSH 变卡"

### 2.1 宿主进程

| 担心 | 结论 |
|---|---|
| 宿主内存被语言服务器吃掉？ | **不会**。语言服务器是独立子进程（孙进程），不占宿主进程内存；宿主自身只多 LSP 管理器 + JSON-RPC 连接的几 MB |
| 宿主 CPU 被占满？ | **不会**。LSP 管理器是 I/O 等待型 |
| 宿主事件循环被阻塞 → DSH 界面卡？ | **会，但可规避**。朴素实现 412 ms，worker_thread 后 8 ms |

### 2.2 语言服务器子进程

| 担心 | 结论 |
|---|---|
| 白占内存？ | **会**（0.8–2.2 GB）。必须实现空闲自动退出 |
| 后台偷跑 CPU？ | **不会**，空闲 0 占用 |
| 大项目索引时和 DSH agent 抢 CPU？ | **会**（吃满一个核数秒~数十秒）。本机 4 核可承受，但应降优先级 |
| **把整机拖进换页？** | **会**（⚠️ 4.2 GB → OOM）。**这是必须设内存上限的直接理由** |

### 2.3 浏览器

| 担心 | 结论 |
|---|---|
| 补全弹窗掉帧？ | 不会。CodeMirror tooltip 是轻量 DOM；实测补全 84 ms / 73 KB |
| 引用面板渲染卡？ | 小符号 98 处 / 16.7 KB 无压力；**大符号可能数千处命中** → 必须虚拟滚动或截断，否则一次 `references` 刷出上万个 DOM 节点 |
| 包体积影响启动？ | +15%，一次性成本，可忽略 |

## 3. 缓解措施（按性价比排序）

| # | 措施 | 代价 | 消除的风险 |
|---|---|---|---|
| **M1** | **设死语言服务器内存上限**（`initializationOptions.maxTsServerMemory`，如 2048 MB） | ~0.3 人天 | **GB 级内存膨胀 → OOM → 整机换页** ⭐ 最高优先级（实测 4.2 GB 崩溃的直接对策） |
| **M2** | **LSP 客户端整体放进 Node `worker_thread`**（进程管理 + JSON-RPC + 解析全在 worker 内），宿主主线程只转发字节 | ~0.5 人天 | **宿主事件循环阻塞（412 ms → 8 ms）** ⭐ DSH 已有先例（`dsh-workflow-worker-thread`、`dsh-code-runtime-worker-thread`） |
| **M3** | **调高请求超时**（`timeout: 3000` → 30 s）+ "索引中…"状态反馈 | ~0.5 人天 | 大项目上"点了没反应"的静默失败 ⚠️ 必修 |
| **M4** | **空闲自动退出**（N 分钟无活动 → kill 进程，按需重启） | ~0.5 人天 | 白占 0.8–2.2 GB |
| **M5** | **崩溃自动恢复 + 明确提示**（exit 134 / 服务器消失 → 重启一次 + 告知用户"项目过大，已跳过语义分析"） | ~0.3 人天 | OOM 后功能永久失效且无提示 |
| **M6** | **启用增量同步**（`@codemirror/lsp-client` 支持），didChange 只传增量 | ≈0 | 1 MB 全文同步的 37.9 ms 解析 → 0.3 ms |
| **M7** | **引用面板虚拟滚动 / 命中数上限**（如 2000 条 + "还有 N 条"） | ~0.5 人天 | 大符号 DOM 爆炸 |
| **M8** | **子进程降优先级**启动（Windows 低优先级） | ~0.2 人天 | 索引期与 agent 抢 CPU |
| **M9** | **用 `ctx.subprocess.spawn` 而不是裸 `node:child_process`** | ~0 | **宿主 API key 泄漏进语言服务器进程**（见 §5） |
| **M10** | 响应体大小上限 + 超限降级 | ~0.3 人天 | 病态载荷（8.9 MB） |

**M1 + M2 + M3 + M4 + M5 合计约 2.1 人天**，即可把"装了插件之后 DSH/整机变卡"的风险降到接近零。

## 4. 消不掉的成本（体验成本，不是性能成本）

### 4.1 首次索引延迟

小项目 `initialize` 只要 419 ms；但大型 TS 项目上 tsserver 需要为整个项目建 program。**实测 3,120 文件 / 81.6 MB 的项目上，语义请求超过 10 分钟仍未返回**（中途 tsserver OOM 崩溃）。

| 阶段 | 用户看到什么 | 应对 |
|---|---|---|
| 0–30 s | 无补全 | 状态栏"语言服务器启动中…" |
| 30 s – 数 min | 无补全 / 无跳转 | "索引中（首次较慢）"+ **可取消** |
| 完成后 | 全功能 | — |

这是 IDEA / VS Code 用户也有的体验（VS Code 打开大 TS 项目时右上角也有 TypeScript 状态条），可接受，但**必须有明确反馈**，否则用户会认为插件坏了。

⚠️ 叠加 §1.5 的默认 3 秒超时：大项目上首个请求会**静默超时**。M3 是必修项。

### 4.2 内存峰值

稳态 0.8–2.2 GB 已实测；4.2 GB 的崩溃峰值也实测到了。**M1 是唯一有效的控制手段** —— 没有上限，tsserver 会一路吃到机器扛不住为止。

### 4.3 并发语言服务器数量

每个语言 × 每个工作区根 = 一个进程。同一 DSH profile 里同时开 TS + Python 项目 → 2 个进程（~2.2 GB + ~0.5 GB）。

**建议：同一时刻只保留当前工作区根的语言服务器，切项目时关掉旧的。**

## 5. 顺带发现的安全问题

`@deepseek-ai/dsh-subprocess` 提供 `scrubbedParentEnv()` 与 `SENSITIVE_ENV_PATTERN`，用于**阻止宿主环境变量（如 `DEEPSEEK_API_KEY`）泄漏进子进程**。

语言服务器是第三方程序，**不应拿到 DSH 的模型密钥**。

> ⚠️ **必须用 `ctx.subprocess.spawn({ argv, cwd, stdio: { stdin: 'pipe', stdout: 'pipe', stderr: 'pipe' } })`，不要用裸 `node:child_process.spawn`。**
> 裸 spawn 会把整个父进程环境继承给语言服务器。DSH 的 `subprocess` service 正好支持 LSP 需要的 per-stream stdio 模式，且**从不把 argv 交给 shell 解释**（与插件现有 git 做法一致）。

## 6. 与现状的对比基线

插件**今天**已经给 DSH 宿主带来这些开销：

| 现状 | 量级 |
|---|---|
| git 状态轮询 | **每 2 秒 spawn 一个 `git status --porcelain=v2` 进程**（`store.js:1083` + `host/git.js:269`）→ 约 **30 次/分钟** |
| 终端 WS | 常驻连接 |
| 常驻子进程 | **无** |

也就是说宿主今天已经在高频 spawn 子进程了。LSP 引入的是**内存型常驻进程**，与现有的**进程数型负载**性质不同：

- 现有负载的痛点：进程创建开销与 CPU 抖动
- LSP 的痛点：**内存驻留 + 首次索引延迟**

两者不叠加，但 LSP 的内存量级（GB）远大于现有负载。

---

## 7. 给决策者的三句话

1. **内存是真正的风险，不是 CPU。** 语言服务器稳态 0.8–2.2 GB，中心依赖型大项目冲到 4.2 GB 后 OOM —— **不设内存上限就会把用户整机拖进换页**（实测）。
2. **CPU 可控。** 空闲不烧核；只在建 program 时吃一个核，本机 4 核可承受。
3. **DSH 宿主本身不会被拖慢**，只要把 LSP 客户端放进 `worker_thread`（DSH 自己已有先例）—— 事件循环漂移 412 ms → 8 ms。

**结论：性能不是否决项，但需要先补上 M1–M5 这约 2 人天的"防护层"，否则上线后一定会收到"装上之后整机变卡"的反馈。**

## 附录：测量方法与局限

| 测量 | 方法 |
|---|---|
| 进程树 RSS | PowerShell `Get-CimInstance Win32_Process` 取 `WorkingSetSize`，按 `ParentProcessId` 还原进程树（含 tsserver 孙进程） |
| CPU | 同上取 `KernelModeTime + UserModeTime`（100 ns 单位） |
| 请求延迟 | 裸 LSP 帧（`Content-Length` 头）直连 stdio，自建客户端计时 |
| 宿主 JSON 成本 | `process.hrtime.bigint()` 包裹 `JSON.parse` / `JSON.stringify` |
| 事件循环漂移 | 25 ms `setInterval` 探针，实际间隔减期望间隔 |
| 真实 socket 中继 | 宿主进程内起 `ws` 服务端 + 客户端实测收发 |
| 测试项目 | 合成 TS 项目（带 `tsconfig.json`），三种形态：中心依赖+strict / 浅依赖+非 strict / 大型中心依赖 |

**已知局限**：
- 合成项目是**压力形态**，不等同于真实仓库；真实项目的 tsserver 内存差异很大（社区经验值 1–4 GB）。绝对值请当作量级参考。
- 只测了 TypeScript。**Python（basedpyright）、Java（jdt.ls，需 JVM，内存通常 1 GB+）、Rust（rust-analyzer）需要各自单独测量** —— jdt.ls 的 JVM 开销是已知的 GB 级，**建议上线前补测**。
- 全部测量在单台 4 核 / 16 GB 笔记本上完成，未在低配机（8 GB）上交叉验证。
- 未测多语言服务器并发的叠加效应。
