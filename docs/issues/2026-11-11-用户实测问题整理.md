## 2. Issue 明细

### ISSUE 1 — 聊天文件链接重复点击，第 2 次起落到侧栏标签

> **原始描述**：点击 chat file link → 通过 IDE 工作台打开 → 再次点击 chat file link → 通过侧边栏标签打开；（同一行）

#### 2.1 用户诉求（精确重述）

- 聊天消息里的**同一个**文件链接：**第 1 次**点击，文件在 **IDE 工作台**内打开（Project 树展开 + 编辑器区定位）。
- **再次点击同一链接**（同一行、同一个链接），期望与第 1 次**完全一致**（仍进 IDE 工作台 / 复用已有文件标签页）。
- 实际：第 2 次点击不再进入工作台，而是**留在 / 打开到 DSH 宿主右侧栏的标签页**。
- 归纳为两条硬要求：**① 确定性**——同一链接的多次点击必须落在同一宿主，不得随点击次数漂移；**② 无残留**——右侧栏不得留下点击后卡死/空白的承载标签页。

#### 2.2 当前行为（代码路径）

**插件用的是宿主提供的"两步承载 tab 协议"**【事实】：

```
聊天链接
  → [宿主] ctx.sidebarRight.openResource(fileAddressFor(sessionId, cwd, path))
  → [宿主] 建承载 tab：kind='ide-workbench'，contentId=文件地址
  → [插件] FileLinkBridge 解析地址 → store.openExternalFile → 在工作台里打开文件
  → [插件] ctx.sidebarRight.openTab(PANEL_ID, { replaceTab: 承载tabId })
             ↑ 用"IDE 工作台页面 tab"替换承载 tab
```

**根因链**：

1. **第 1 次点击**【事实 + 宿主事实】：工作台页面 tab 尚不存在 → 宿主执行 `replaceTab`（关闭承载 tab、创建工作台页面 tab）→ **完全正常**，与用户描述一致。
2. **第 2 次点击**【事实 + 宿主事实】：新建承载 tab → `openExternalFile` 再次返回 `'opened'` → `replaceWithIde()` 调 `openTab(PANEL_ID, {replaceTab})`，但这次**工作台页面 tab 已存在** → 宿主只做 `focusTab`，**跳过 replace、承载 tab 不被关闭**。
   插件对此**完全无感**：`openTab` 不抛异常 → `replaceWithIde()` 返回 `true` → `index.jsx:111-114` 的 `if (!replaceWithIde())` 不成立 → **`view.phase` 永远停在 `'opening'`** → 残留标签页**永远显示"加载中"**。
3. **第 3 次及以后**【宿主事实】：残留的承载 tab 持有 `(kind='ide-workbench', contentId=文件地址)`，正好命中宿主的 `findContentTab(layout, contentId, kind)` 去重键 → 宿主**只聚焦、不新建、也不触发 `FileLinkBridge`** → **这次点击根本没有到达工作台**。

> 【宿主事实】宿主的 `place()` / `openContent()` 只在**目标页面 tab 尚不存在**（`revealed === undefined`）时才 push `closeTab(replace)`；已存在同 `(kind, contentId)` 的 tab 时只 `focusTab`。排序规则：`priority` band（`extension:3 > builtin:2 > fallback:1`）→ 匹配到的 pattern 长度 → 注册顺序；`canOpen` 为假则整型出局。

### ISSUE 2 — 回合变更预览链接只能在侧栏打开，无法在 IDE 工作台内看 diff

> **原始描述**：一轮对话结束后，如果有文件变更，会在结尾给出变更预览的链接（点击后展示为 diff），聊天中给出的变更链接 → 仅能通过侧边栏标签打开 → 而非 IDE 工作台

#### 2.1 用户诉求（精确重述）

- 一轮对话结束后，若该轮有文件变更，聊天消息末尾给出**变更预览链接**（点击后展示 diff）。
- **实际**：diff **只能**在 DSH 宿主右侧栏的标签页里打开，**无法**在 IDE 工作台内查看。
- **期望**：变更预览的 diff **也能**在 IDE 工作台内打开，与普通文件链接体验一致（理想：链接默认进工作台，工作台内保留"在侧栏打开 / 外部 IDE 打开"等既有出口）。

#### 2.2 当前行为（代码路径）

**关键：变更预览链接根本不是"文件地址"。**【宿主事实】

```js
// 宿主 @deepseek-ai/dsh-client-ui-deliverables
function changesReviewAddress(coordinates) {
  const { sessionId, seq, turn } = coordinates
  return `dsh-resource://changes-review/session/${encodeURIComponent(sessionId)}/${seq}/${turn}`
}
```

### ISSUE 7 — Commit 历史变更详情树要逐层展开 8 次

> **原始描述**：Commit 历史变更详情的树形展开：例如变更的代码只有 `hivemind-agent-engine/src/main/java/com/liangshou/agentic/agents/hooks/StudioForwardMiddleware.java` 要从 hivemind-agent-engine 开始一层一层展开直到 hooks 展开，操作很繁琐，这里的路径设计参考需求点 5 进行优化，若中间路径没有变更文件，直接一步到位，把叶子节点展开

#### 7.1 用户诉求（精确重述）

Git 工具窗打开某个 commit 的详情抽屉后，下方「变更文件」以目录树展示。当本次改动**只有一个深层文件**时，用户必须从 `hivemind-agent-engine` 开始逐级点击展开 `src → main → java → com → liangshou → agentic → agents → hooks` 才能看到文件本身。

诉求：**参考 Issue 5 的路径设计**——当中间路径层级**没有任何变更文件**时，这些目录链**合并为一步直达**，并**把叶子节点直接展开**。

#### 7.2 当前行为

**⚠️ 勘误**：Commit 历史在 **`src/client/GitPanel.jsx`**，不在 `CommitPanel.jsx`（后者是 Commit 工具窗的暂存区面板，与本 issue 无关）。

**构树算法**【事实】—— `src/client/GitPanel.jsx:186-204`：

```js
export function buildChangedFileTree(files) {
  const root = { name: '', path: '', depth: 0, dirs: new Map(), files: [] }
  for (const group of groupByDirectory(files)) {
    const segments = group.dir === '' ? [] : group.dir.split('/').filter(segment => segment !== '')
    let node = root
    let prefix = ''
    for (const segment of segments) {
      prefix = prefix === '' ? segment : `${prefix}/${segment}`
      let child = node.dirs.get(segment)
      if (child === undefined) {
        child = { name: segment, path: prefix, depth: node.depth + 1, dirs: new Map(), files: [] }
        node.dirs.set(segment, child)
      }
      node = child
    }
    node.files.push(...group.entries)
  }
  return root
}
```

`groupByDirectory`（`src/client/commit-model.js:70-81`）按**完整父路径**分组（`parentDirOf` `:12-15`），本函数把父路径按 `/` **逐段拆成真实的多级目录节点**。

### ISSUE 10 — 终端输入过程中切换输入法，已敲内容丢失

> **原始描述**：terminal 输入期间切换输入法（可选，优先级不高）：这个问题常见于原本为中文输入法、输入一些内容后按 Shift 键切换输入法语言时，原先写的内容就直接丢失，对比 Windows 的 terminal 在面临同样的场景时，不会丢失已经敲了的内容，而是会原封不动直接把英文字符串写进去

#### 10.1 用户诉求（精确重述）

在内嵌终端中用**中文输入法**敲入若干字符（处于组字/候选状态）后，按 **Shift** 切换中/英输入法语言时，**已经敲下的字符直接丢失**。

对比 **Windows Terminal**：同样场景下**不会**丢失已敲内容，而是**原封不动把英文字符串写进去**。

期望：切换输入法语言时，终端中已输入的内容必须被**保留并按原样上屏**，不得静默丢弃、不得重复。

#### 10.2 当前行为：**不是本插件的业务代码缺陷**

**插件侧的输入通道只有 `onData` 一条，忠实透传**【事实】：

```js
// src/client/TerminalPanel.jsx:173
const dataDisposable = terminal.onData(data => send({ type: 'input', data }))
// src/client/TerminalPanel.jsx:77-80  send() → WebSocket JSON 帧
// src/index.js:754-771  ws.on('message') → if (frame.type === 'input') write(frame.data)   (:762)
// src/index.js:749-753  write() → handle.write(data)
```

⇒ **插件→宿主→PTY 的通道是忠实的**：xterm 给出什么就写什么，没有过滤、没有截断。

**插件完全不碰 IME / 组合**【事实】：对 `src/client/**` 全量 grep `composition|isComposing|attachCustomKeyEventHandler|onKey|onBinary` ⇒ `composition` / `isComposing` / `terminal.onKey` / `attachCustomKeyEventHandler` / `terminal.textarea` **全部 0 命中**。插件创建 xterm 时开了 `allowProposedApi: true`（`TerminalPanel.jsx:59`）但**没有使用任何 proposed API**。

**插件自己的两个 keydown 监听器对 Shift 完全透明**【事实】：

1. `TerminalPanel.jsx:201-217`（终端宿主上的 capture 监听）只处理 `Ctrl+Shift+V` / `Ctrl+C` / `Ctrl+F` ⇒ 纯 Shift 时 `event.ctrlKey === false`，**三个分支都不进**，不 preventDefault、不 stopPropagation。
2. `src/client/index.jsx:568-659`（document capture）走 `matchesShortcut`（`util.js:39-42`）+ `comboOf`（`util.js:16-22`）⇒ 纯 Shift 得到 `'shift+shift'`，**不匹配任何已配置快捷键**。

**真正的丢失点在 xterm.js 的 `CompositionHelper`**【事实】（`node_modules/@xterm/xterm`，版本 **6.0.0**，来自 npm 非 CDN）：

#### 11.3 根因定位

**根因 A（实测）：Windows 分支用「URL 协议处理器」去打开 `file:` URL，而 `file:` 不是一个有 open 动词的 URL 协议**【事实 + 实测】

`src/host/shell.js:40-43` 让所有协议都走 `rundll32 url.dll,FileProtocolHandler`。该入口是 Windows 的 **URL 协议处理器**（`HANDLEURLPROTOCOL`）钩子，只能派发**已注册的 URL 协议**（`http:`、`https:`、`mailto:` …）。`file:` 在 Windows 上由 shell 内部按「文件关联」处理，而不是按 URL 协议派发。

> ⚠️ **修正一个常见误解**：不是"`file:` 的默认处理器是资源管理器"。实测（Windows 11）：`HKCR\file` 只有 `CLSID` 子键、**没有 `shell\open\command`**（即没有 open 动词）；`HKCR\htmlfile` → 已退役的 `iexplore.exe`。
>
> 用插件**完全相同的 spawn 参数**（`detached:true, stdio:'ignore', shell:false, windowsHide:true`）实测：
>
> | 用例 | URL | 结果 |
> |:--|:--|:--|
> | D | `file:///C:/Windows/System32/notepad.exe` | `spawn ok`，**没有任何新进程** |
> | E | `file:///C:/.../dsh-iwb-probe.txt` | `spawn ok`，**没有任何新进程** |
> | F | `file:///C:/.../dsh-iwb-probe.html` | `spawn ok`，**没有任何新进程** |
>
> （`iexplore` 进程数始终为 0；Chrome 进程的命令行里查不到探测文件；`ShellExecute("open","file://…")` 返回 hresult=42「已接受」但也没有窗口；不存在的文件返回 hresult=2，说明 shell 只做了路径解析、没有派发动作。）
>
> ⇒ **`rundll32 url.dll,FileProtocolHandler` 对 `file://` 一律「启动成功但什么都不做」，而且 rundll32 自己不报错** —— 与用户描述的"默认浏览器几乎不生效"完全吻合。

**根因 B：成功判定建立在 `spawn` 事件上，失败无法被感知**【事实】

`src/host/shell.js:44-54` 的 Promise 只在 child 的 **`'spawn'`** 事件时 resolve（`:53`），**从不检查退出码**，`stdio:'ignore'` 又丢掉 stdout/stderr，`windowsHide:true` 连控制台都不给 ⇒ 宿主永远回 `{ opened: true, url }`（`:55`）⇒ 客户端 `store.js:853-854` 永远走成功分支，**不会**走到 `toast('error', 'browser.openFailed')`（`:856`）。

⇒ **这就是"静默失效"：用户连报错都看不到。**

**根因 C（次要）：「默认浏览器」与「文件关联」被混为一谈**【事实】

- Windows 的**默认浏览器**由 `HKCU\...\UrlAssociations\http\UserChoice` 决定（本机是 `ChromeHTML` → `chrome.exe --single-argument %1`）；**`file:` 没有 UserChoice**。
- ⇒ 即使把 `file://` 正确派发出去，它走的也是 `.html` 的**文件关联**（本机 = 已退役的 IE；正常 Win11 = Edge），**不一定是 Chrome**。
- 但按钮画的是硬编码 Chrome 图标（`EditorArea.jsx:612` `iwb-chrome` + `IconChrome`），文案是"用默认浏览器打开"（`i18n.js:412/896`）⇒ **图标/文案承诺的是"用户默认浏览器（Chrome）"，实现却只能触达"`.html` 文件关联"** —— 期望与实现的语义错位本身就是要修的点。

**根因 D（次要）：打开的是磁盘文件，不是编辑器缓冲区**【事实】

`tab.path` 是绝对磁盘路径（`store.js:2219-2221`），文件一定存在（内容来自 `fs.read` → `host/workspace.js:272-338`），所以 `file://` **本身不是错的 URL**。但如果标签页有未保存修改（`tab.dirty === true`，草稿在 `tab.draft`，`EditorArea.jsx:147-149`），磁盘上的文件是旧的 ⇒ 浏览器打开的是旧版本，看起来也像"不生效"。

### ISSUE 12 — Markdown / TXT 的字数统计（新增需求，✅ 口径与实现细节已拍板）

> **原始描述**：对 markdown、txt 这类的文件加一个词数/字数统计 —— 需要先评估实现的性能开销代价和实际收益

#### 12.1 结论先行

| 问题 | 结论 |
|:--|:--|
| 该不该做？ | **该做**，但价值集中在**中文写作 / 长文编辑**场景；它不是"补齐 IDE 缺失功能"（VS Code 也没有），而是**对标 IntelliJ IDEA**（IDEA 自带 Tools → Word Count + 状态栏词数），与插件"JetBrains 风格"的定位一致 |
| 性能代价有多大？ | **取决于算在哪**。放在 render 路径 = 灾难；放在 store 的加载/保存路径 = **可忽略（一次性 ~5 ms）** |
| 最大的坑是什么？ | **现有状态栏的 `lines` 计数已经在 render 路径里现算**（`Workbench.jsx:325-327`）。照着它加字数 = 把一个既有的 O(n) 性能债再叠一层 |
| 绝对不能做什么？ | **不能用 `Intl.Segmenter`**：实测 **608 ms / 2 MiB**，每次按键都会卡住 0.6 秒 |
| **最终方案（已拍板）** | **方案 1**：在 store 的加载/保存路径算一次，存进 `tab.stats`，状态栏只读；**口径 B**、**只给「字数」**、**只统计已保存内容**、**只对 markdown / txt 生效**、**不排除 Markdown 语法符号** |

#### 12.2 现状：状态栏已经存在，而且**已经有一个 O(n) 的行数统计**

**状态栏早已存在，且位置正合适**【事实】—— `src/client/Workbench.jsx:320-375`：

已有 4 项：`Ln:Col`、`行数`、`编码+换行符`、插件状态项插槽。**加一项"字数"的边际 UI 成本 ≈ 0**。

⚠️ **注意 `lines` 的语义**：它统计的是 `active.payload.content` —— 即**最后一次从磁盘读到的内容**，**不是**当前编辑缓冲区（`tab.draft`）。所以现有状态栏**本来就不跟随未保存的编辑**。

#### 12.3 性能开销评估（这是本 issue 的核心）

##### (a) 触发频率：状态栏几乎在**每一次 store 通知**时重渲染

【事实】`src/client/Workbench.jsx:519`：`const state = useWorkbench(store)` → `useSyncExternalStore(store.subscribe, store.getSnapshot, store.getSnapshot)`（`src/client/hooks.js:4-5`）⇒ **订阅的是整个 store 快照**，任何 `store.set()` 都会让 Workbench 重渲染 → StatusBar 重渲染 → `split('\n')` 重跑。

`store.set()` 的触发源：

| 触发源 | 位置 | 频率 |
|:--|:--|:--|
| **每次按键** | `CodeEditor.jsx:492` `if (update.docChanged) onChange(doc.toString())` → `EditorArea.jsx:162` → `store.updateDraft`（`store.js:2441`）→ `#updateTab` → `this.set({tabs})` | 打字时连续 |
| **每次光标移动** | `CodeEditor.jsx:493` `if (update.selectionSet \|\| update.docChanged) onCursor(...)` → `EditorArea.jsx:164` → `store.setCursor`（`store.js:3590-3594`）→ `this.set({cursor})` | 方向键 / 鼠标点击 |
| **每 2 秒** | `store.js:1295` `setInterval(() => { void this.pollStatus() }, 2000)` → `store.js:1426` `this.set({ status, statusError, statusAt: Date.now(), statusStale })` | ⚠️ `statusAt: Date.now()` **每次都变** ⇒ 即使 git 状态没变也照样 `set()` ⇒ 照样重渲染 |
| 标签切换 / toast / 终端输出 / 设置变更 | 多处 | 不定 |

##### (b) 单次成本：**在插件的实际上限（2 MiB）实测**

【事实】文本内容上限由 host 决定 —— `src/host/workspace.js:28` `const MAX_TEXT_BYTES = 2 << 20`（**2 MiB**），`:298-305` 超过即截断。
【事实】可编辑上限 `settings-store.js:99` `editableMaxBytes: 1 << 20`（**1 MiB**，超出以只读打开）。

**实测（Node 22，2 MiB 中英混排 Markdown，20 次取平均；浏览器同引擎同量级）**：

| 策略 | ms / 次 | 备注 |
|:--|--:|:--|
| `text.split('\n').length` | **3.65** | ← **状态栏现有的行数统计** |
| `text.match(/\S+/g).length` | **16.10** | 拉丁词数；会分配一个 7.5 万元素的数组 |
| `text.replace(/\s/g,'').length` | **14.32** | 字符数（不含空白） |
| `text.replace(/[^\x00-\x7F]/g,'').length` | **8.02** | CJK 字符数 |
| **手工单遍扫描（CJK 逐字 + 拉丁按词）** | **4.77** | 只比现有的 `split` 多 1.1 ms |
| `Intl.Segmenter('zh', {granularity:'word'})` | **607.72** | ⚠️ **不可用** |

**实测脚本**：2 MiB / 1,531,578 UTF-16 单元 / 75,890 行。

##### (c) 把成本换算成"主线程占用"

以 2 MiB 文件、每秒 8 次按键 + 每秒 2 次 git 轮询 ≈ **10 次 render/秒** 计：

| 方案 | 每次 render | 主线程占用 |
|:--|--:|--:|
| 现状（只有 `split`） | 3.65 ms | ≈ **3.7 %** |
| 现状 + 朴素 `match(/\S+/g)` | 19.75 ms | ≈ **19.8 %** ⛔ |
| 现状 + 手工单遍扫描 | 8.42 ms | ≈ **8.4 %** ⚠️ |
| 现状 + `Intl.Segmenter` | 611 ms | **> 6000 %** ⛔⛔ 卡死 |

**但这是最坏情况。** 真实的中文 markdown 文档通常 **10 KB – 100 KB**，所有开销按比例缩小 **20–200 倍**：

| 文档大小 | `split`（现状） | 朴素 `match` | 手工单遍 |
|:--|--:|--:|--:|
| 10 KB | ≈ 0.02 ms | ≈ 0.08 ms | ≈ 0.02 ms |
| 100 KB | ≈ 0.18 ms | ≈ 0.81 ms | ≈ 0.24 ms |
| 2 MiB（上限） | 3.65 ms | 16.10 ms | 4.77 ms |

⇒ **结论：真正的风险不是"计数本身贵"，而是"在一个每次按键都重渲染的组件里做计数"。** 把同样的计数从 render 路径挪到加载路径，2 MiB 的文件也只要 **5 ms 一次性**。

##### (d) 一个必须一起看的既有性能债

【事实】逐键路径上**已经有 4 次 O(n) 全串操作**（2 MiB 时每次按键约 4×3.65 ≈ 15 ms）：

| # | 位置 | 操作 |
|:--|:--|:--|
| 1 | `CodeEditor.jsx:492` | `update.state.doc.toString()` —— 整篇拷贝 |
| 2 | `store.js:2444` | `normalizeNewlines(tab.payload.content)` —— `text.replace(/\r\n/g,'\n')` 全串拷贝 |
| 3 | `store.js:2445` | `normalizeNewlines(text)` —— 又一次全串拷贝 |
| 4 | `store.js:2446` | `draft !== saved` —— 全串比较 |
| 5 | `Workbench.jsx:326` | `text.content.split('\n')` —— 状态栏行数 |

⇒ **字数统计如果做成第 6 次逐键 O(n)，是把一个既有问题从 5 变成 6**；如果做成"加载时算一次"，则是 **0 次逐键开销**。

#### 12.4 实际收益评估

| 维度 | 评估 |
|:--|:--|
| **谁用得上** | 写中文长文的用户（PRD / README / 方案文档 / 博客）。对纯代码文件意义不大 |
| **对标品** | **IntelliJ IDEA**：有（状态栏 + Tools → Word Count）—— 与插件定位一致<br>**VS Code**：**没有内置**（需装扩展）—— 所以这不是"补齐 VS Code"<br>**Typora / Obsidian / Word**：都有 —— 这才是用户期待的形态 |
| **增量价值** | 中。状态栏已经给了 `行数` / `编码` / `换行符` / `Ln:Col`，字数是同一类"文件元信息"的自然补充，边际成本低 |
| **会不会被用坏** | 如果只给"英文词数"，中文用户会觉得"数字不对"（中文没有词边界）⇒ **口径比功能本身更重要** |
| **不做会怎样** | 用户只能切到别的工具数，或用 `wc -m` / `wc -w`（终端里其实能做）⇒ **不是阻塞性缺失** |

⇒ **收益定位：低成本、低风险、中等收益的"锦上添花"**。建议 P2，可选做，但**一旦要做就必须做对**（口径 + 位置），否则会变成一个"数字不对还没人用"的功能。

#### 12.5 三个方案

| 方案 | 做法 | 逐键成本 | 准确性 | 工作量 |
|:--|:--|:--:|:--|:--|
| **方案 1（推荐）：状态栏显示"已保存内容"的统计** | 在 `store.ensureTabContent`（`store.js:2291-2302`）加载完成时算一次，存进 `tab`（如 `tab.stats = { chars, words }`），状态栏只读这个数 | **0** | 与现有 `lines`/`encoding` 语义**完全一致**（都是已保存内容）—— 编辑中数字不变，保存后更新 | 小（store + 状态栏一行 + i18n 两个键） |
| **方案 2：实时统计（跟随编辑）** | ① 用 CodeMirror 的 `update.changes` **增量**重算（只扫改动区间）② 或在 `updateDraft` 里 **150–200 ms 防抖** 后算 | 增量 ≈ 0；防抖 ≈ 每 200 ms 一次 5 ms（2 MiB） | 实时 | 中（增量算法要处理 UTF-16 边界与 CJK 跨字） |
| **方案 3：按需弹窗** | 工具菜单 → "字数统计"，打开时算一次（IntelliJ 的 Tools → Word Count） | **0** | 精确（可给详细分解：字符/词/行/段落/中英文分别统计） | 小 |

**推荐组合：方案 1（默认，状态栏一行）**。✅ **已拍板采纳方案 1**，方案 3（详细弹窗）本期不做。

- 两者都**不在 render 路径里做计算**；
- 方案 1 顺手可以把现有的 `lines` 计数也挪进 `tab.stats`，**一次性偿还既有的 render 路径性能债**；
- 方案 3 承担"用户想要精确值 / 想要详细分解"的诉求 —— **本期不做**。

**明确不做**：`Intl.Segmenter`（608 ms @ 2 MiB）；在 `StatusBar` 函数体里现算任何 O(n) 的量；实时（跟随编辑）统计；词数独立展示项；详细统计弹窗。

#### 12.6 计数口径（✅ 已拍板：口径 B，只给「字数」）

中文没有词边界，"词数"和"字数"在中文语境里是**两件事**。三种常见口径：

| 口径 | 定义 | 适合 | 代价 |
|:--|:--|:--|:--|
| **A. IntelliJ 式** | `Words`（按空白切分）+ `Characters`（不含空白）**两项都给** | 英文文档准确；中文的"Words"是空白分段数，**对中文无意义** | 最便宜（一次 `split` + 一次 `replace`） |
| **B. 中英混排式** | **CJK 逐字计数 + 拉丁按词计数**，相加 | 中文写作的真实需求（"我写了 3500 字"） | 需要一次手工单遍扫描（4.77 ms @ 2 MiB）—— 仍是**最便宜的真·中文口径** |

**✅ 已拍板（2026-11-11）**：
- ① **只给"字数"**（不额外给"词数"）→ 采用**方案 1**（加载/保存时算一次，存进 tab，状态栏只读）
