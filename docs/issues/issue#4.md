## 二、需求详述

### N1 — 文件树内文件搜索

**优先级** P1 ｜ **类型** 缺失

> **范围**：Project 面板的【筛选文件】输入框。

#### N1.1 树搜索（【树】Tab）

**现状**

当前的行为是"仅过滤已展开的目录"：键入搜索后，依旧把所有的文件目录树都渲染出来，保留搜索前的展开状态。

**痛点**

- 对于文件搜索来说，不包含目标文件的目录路径是纯粹的干扰信息；
- 搜索文件的目的本身就是为了快速定位文件的位置，如果目标文件所在目录没有被展开，在当前行为模式下，还是要一个个目录展开，搜索变得毫无意义。

**期望**

1. 键入搜索后，文件树中仅保留**包含目标文件的完整目录路径**，无关路径需要隐藏——需要考虑性能因素，可以是类似于`可见性`的属性做到**软隐藏**，而不是把整棵树都给彻底重新渲染；
2. 目录**自动展开**，直到达到目标文件（叶子节点）：例如目标文件的目录是 `DSH-IDE-TOOLWINDOWS-ROOT\dsh-ide-workbench\packages\codeintel\src\contract\client-api.d.ts`，`DSH-IDE-TOOLWINDOWS-ROOT` 为 Project 打开的根目录。键入搜索以后，应当把 `\dsh-ide-workbench\packages\codeintel\src\contract\` 一条完整的目录路径给自动展开，直达根节点，文件树中只有包含了目标文件的目录路径可见；
3. 搜索**按文件名前缀匹配**：例如 Project 中同时有 `client-api.d.ts`、`client-api.ts`、`client-api.js`，键入 `client-api` 搜索时，前述的几个文件都命中前缀匹配；
4. 键入搜索后，默认的 Tab 是【树】，这一行为**不得改变**；
5. **性能与速度**：尤其关注搜索的性能，需要最优的解决算法。

#### N1.2 文件搜索（【文件】Tab）

此部分暂无明显的功能性缺陷，只需注意性能与速度即可：在某些机器上，当文件数量非常多时，检索速度非常慢，长时间没有响应，导致用户误以为没有检索到目标文件。

**根因提示（已取证）**

- 树模型 `flatten()` 把 `state.filter` 当作 memo 输入 → **每敲一个字符整棵树重建一次**；在【文件】Tab 下这份计算 100% 白做（`flatten` 在该模式下把过滤串置空），然后被 `quickRows` 整个丢掉。
- 【文件】Tab 的过滤是 `rel.toLowerCase().includes(query)`：**每个键击对全部索引项做一次 `toLowerCase()`**（5 万个文件 = 5 万个新字符串），且先 `.filter()` 出全部命中再 `.slice(0, 300)`，没有早停。
- 树是**懒加载**的：宿主只知道被加载过的目录的孩子，所以"某个未加载目录里有没有命中文件"树自己答不了 —— 全项目文件索引（`fs.files` → `host/search.js:listFiles`）才是唯一的事实来源。

**已定**

- 默认 Tab 改为【树】（`store.js` 的 `filterMode` 初值 `files → tree`，Tab 按钮顺序改为【树】【文件】）；
- 前缀匹配**大小写不敏感**（与仓库内其它过滤器一致：`ProjectPanel.jsx` 的旧过滤、Quick Open 的 `quickScore`）；
- 匹配对象是**文件名**（不是整条路径）：`client-api` 命中 `client-api.d.ts` / `.ts` / `.js`，**不**命中 `my-client-api.ts`；
- 树搜索复用【文件】Tab 的全项目索引，两 Tab 共用一份索引与一次宿主调用。

### N2 — 文件编辑保真

**优先级** P0 ｜ **类型** Bug（阻塞性）

> **范围**：内容区域中，所有文件编辑录入符号如 `#`、`*`、`+` 等等的场景，包括但不限于 txt、md、python、yaml、.properties，几乎在所有文件中都见到过。

**现状描述**

- 编辑行开头录入连续 `#` 后，强行变格式，吞掉前面的 `#` 符号，例如录入 `###`，会立马渲染成 `#` 或者 `##`，至多显示出 2 个 `#`；
- 编辑行开头录入 `#` 后再录入空格时，也会强行吞掉若干 `#`、强行改渲染格式；
- 在有内容行的行中编辑时暂未发现；
- 录入内容在文件中实际并未丢失，纯表现为强行转换格式；
- 其余符号，如 `*`、`+`、`/`、`.` 等，绝大多数符号都有类似的情况：吞前面的字符序列、强行渲染、增改缩进等等。

**期望**

唯一原则：在编辑模式下，所有的文件内容都应当 100% 保真，不得画蛇添足去渲染。

**根因提示（已取证）**

- **不是 markdown 的锅**。用真实的 `EditorView`（jsdom）+ `CodeEditor.jsx` 的完整扩展表复现：md / py / yaml / 纯文本 / `.properties` 下，键入 `###`、`# `、`*`、`+` 的**文档与可见文本都逐字符保真**。`@codemirror/lang-markdown@6.5.2` 没有任何 `Decoration.replace`、没有输入处理器，它唯一的键位是 `Enter → insertNewlineContinueMarkup` 与 `Backspace → deleteMarkupBackward`。
- **真凶是语言服务器补全**：
  1. `@codemirror/lsp-client@6.3.0` 的 `serverCompletionSource` 用**服务器**给的区间（`completionResultRange`）按字符偏移映射到当前行；服务器用的是它自己那份文档副本，区间因此会盖住用户刚敲进去的字符；
  2. `@codemirror/autocomplete@6.20.4` 在**键入 commit character 时自动接受补全**（`applyCompletion`），没有任何用户动作 —— 语言服务器报的 commit character 恰好就是用户点名的 `#`、`*`、`+`、`/`、`.`；
  3. `applyCompletion` 写入的文本自带缩进 —— 这就是"增改缩进"。
- 本仓库 HEAD 上**按文件的 LSP 插件没有装**（`packages/codeintel/src/client/lsp-session.js` 导出了 `lspPluginExtension(path)`，但没人调用），所以这份构建里症状看不见（语义编辑能力整体是关的）；用户实际运行的**扁平布局构建（0.5.0）装了它**，所以症状成立。修复必须两边都成立。

**已定**

- 补全**不再有 commit character**：敲 `#`/`*`/`+` 永远不会静默接受补全，接受只走 Enter/Tab（与 VS Code 的 `acceptSuggestionOnCommitCharacter: false` 一致）；
- 补全的替换区间**夹到光标处的单词**上，永远吃不到光标之前的字符；
- 核心（workbench）另加一道**保真守卫**：插件装进来的破坏性扩展不得静默改写用户文本，同时不得破坏补全本身、括号自动闭合、`indentOnInput`、markdown 列表续行、折叠、查找栏与 blame 栏。

### N3 — 全局搜索提速

**优先级** P1 ｜ **类型** 体验（当前表现为长时间无响应）

> **范围**：只安装 core 插件的情况下，Ctrl+Shift+R 进行全局搜索。

**现状描述**

功能性不存在问题，性能需要提高，需要探索一下检索速度是否存在提升空间。目前已经发现了，在工作区文件很多的一些情况下，全局搜索长时间甚至彻底无响应。

**根因提示（已取证，实测数字见 `qa-sandbox/search-bench/`）**

1. **非 Git 工作区**走 `searchWithWalk`：`for (const path of files) { await readFile(...) }` —— **串行**。2 万文件 / 59 MB 的分解：list 527 ms ｜ **read 5237 ms** ｜ decode 39 ｜ split 51 ｜ regex 36 ⇒ **94 % 是那个串行读循环**。有界并发池（32）= 2.2–2.6×；外部扫描器 = 4.2–5.4×。
2. **Git 快速路径反而更慢**：`searchWithGit` 之后 `attachContext` 把**每个命中的文件再读一遍**补上下文，而这发生在截断到 2000 条**之前** ⇒ "到处都命中"的查询下 **9815 ms vs 走查路径的 526 ms（19×）**。`git grep -C 5` / `rg -C 5` 直接带上下文，这段重读可以整个删掉。
3. `--untracked` 让 git 走遍整个工作树：比只扫已跟踪文件贵 14–18×。
4. 客户端每敲一个字符发一次全量扫描，**从不取消**上一次；打开弹窗时同一个查询还会扫两遍。
5. **上限会撒谎**：走查路径命中 3000 条只返回 2000 条，却报 `truncated=false`；`MAX_FILES`（5 万）也是静默截断。

**已定**

- 读文件走**有界并发池**（按并发数与在途字节数双限），结果保持路径序；
- 上下文**由扫描器直接给出**，不再回读命中文件；
- 外部扫描器（`rg`，或非 Git 场景下的 `git grep --no-index`）作为**可选**加速路径，取不到就回落到内置走查，**不新增原生二进制依赖**；
- 截断**如实上报**（`truncated` 与文件上限）；
- 客户端**取消**过期扫描（AbortSignal），一次打开只扫一次。

## 三、验收标准

### N1

- [ ] 键入 `client-api`，树里只出现 `…/dsh-ide-workbench → packages → codeintel → src → contract` 这条链与命中的文件，其余目录不可见
- [ ] 该链**自动展开**到目标文件，父目录逐级加载
- [ ] `client-api.d.ts` / `client-api.ts` / `client-api.js` 三个都命中；`my-client-api.ts` 不命中
- [ ] 默认 Tab 是【树】，且不会在键入时自动跳到别的 Tab
- [ ] 键入不重建整棵树模型（软隐藏：行对象复用，虚拟列表按可见行计算）
- [ ] 【文件】Tab 在数万文件的项目里不再长时间无响应

### N2

- [ ] 行首连续录入 `###`，文档与可见文本都保持 `###`
- [ ] 行首录入 `#` 再录入空格，保持 `# `，格式不被改写
- [ ] `*`、`+`、`/`、`.` 同样不被吞，行缩进不被改
- [ ] 已有内容的行中编辑同样保真
- [ ] txt / md / py / yaml / .properties 全部成立（无语言包的文件也成立）
- [ ] 补全仍可用（Enter/Tab 接受），括号自动闭合、折叠、查找栏、blame 栏不回归

### N3

- [ ] 2 万文件的工作区：全量搜索的墙钟时间显著下降（不再 6–13 s）
- [ ] "到处都命中"的查询不再出现 19× 的反常
- [ ] 过期扫描被取消；打开弹窗只扫一次
- [ ] 命中被截断时 `truncated` 为真
