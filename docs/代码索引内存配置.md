# 代码索引的内存配置：含义、配置方法与已知局限

> **面向对象**：使用 IDE 工作台、并且关心「语义分析要吃多少内存」的人。
> **一句话**：索引占的内存由**语言服务器进程**决定，工作台只能**估算**它；估算值
> 决定「要不要启动 / 要不要问你」，估算值的**上限**决定「估算按多少封顶」，
> 而**只有一种服务器真的按这个上限限制自己**。
> 规格见 `docs/PRD-v5-补充需求.md`（§2.2 / §2.3 / §4.4），本文件是**面向使用者的说明**。

---

## 1. 两组数字，含义完全不同

最常见的误解是把「上限」和「估算」当成一回事。它们是两个独立的数。

| | 字段 | 含义 | 谁在用 |
|---|---|---|---|
| **上限** | `lsp.memoryLimitMB`（全局）<br>`lsp.servers[语言].memoryLimitMB`（按语言） | 交给语言服务器的**内存天花板** | ① 作为启动前估算的封顶；② **只有 TypeScript** 真的把它传给服务器进程 |
| **估算** | `lsp.servers[语言].memoryBaselineMB`（按语言） | 这类语言服务器的**典型占用**（不是最坏情况） | 只用来和「当前可用内存」比，算出要不要启动 |

**内置估算**（MB，未配置时的默认）：

| 语言 | 估算 | 内置上限 |
|---|---|---|
| TypeScript / JavaScript | 256 | 2048 |
| Java | 512 | 2048 |
| Rust | 512 | 2048 |
| C / C++ | 384 | 2048 |
| Go | 256 | 1536 |
| Python | 192 | 1536 |
| YAML | 64 | 512 |
| 未知语言 | 256 | — |

## 2. 生效上限是怎么算出来的

```
生效上限 = 按语言设置的上限            （它「替换」全局上限，可以比全局更高）
         或 min(该语言的内置上限, 全局上限)
```

所以：

- **调低全局上限 → 每个语言都跟着变低**（取两者更小的那个）。
- **调高全局上限 → 对内置上限更高的语言无效**。全局设成 4096，TypeScript 仍然是
  2048 —— 因为它的内置上限就是 2048。
- **要给某一个语言更多 → 用它自己那一行的上限**。按语言的设置是**替换**，不是叠加，
  所以它可以比全局上限更高。

> 这一点在 2026-10-31 的第二轮检视中被反复反馈（「看着还是像 2048」）：全局值调上去了
> 却看不到变化。设置页的提示文案现在写明了这层关系。

## 3. 三道闸门：能不能启动

启动（或崩溃后重启）那一刻，宿主读一次机器的**可用内存**，和估算比：

```
需求 MB = min(估算, 生效上限) × 内存余量系数(默认 1.5)
软阈值  = 需求 MB × 2
```

| 可用内存 | 判定 | 行为 |
|---|---|---|
| `≥ 软阈值` | **可启动** | 直接启动语言服务器 |
| `硬下限 ≤ 可用 < 软阈值` | **内存紧张** | **弹窗问用户**：「仍然启动」或「使用基础模式」 |
| `< 硬下限`（默认 256 MB） | **内存不足** | 直接降级为基础模式，不启动 |

两点补充：

- **硬下限是兜底，也是地板**：小语言也会被它托住。例如 YAML 的需求只有 96 MB，但
  硬下限 256 MB 更高，所以它同样要 256 MB 可用内存才能启动。
- **「保守兜底下限」（默认 512 MB）只在语言未知时生效**。有估算时用的是估算值，
  这个数字不参与判定 —— 它是「连语言都认不出来」时的保守值。

具体到默认配置（可用内存 ≥ 软阈值就直接启动）：

| 语言 | 需求 MB | 软阈值 MB | 实际门槛 MB |
|---|---|---|---|
| TypeScript / JavaScript | 384 | 768 | 384 |
| Java / Rust | 768 | 1536 | 768 |
| C / C++ | 576 | 1152 | 576 |
| Go | 384 | 768 | 384 |
| Python | 288 | 576 | 288 |
| YAML | 96 | 192 | **256 —— 硬下限更高，取它** |

最后一列是真正要跨过的门槛：`max(硬下限, 需求)`。YAML 的需求只有 96 MB，但硬下限
256 MB 更高，所以它同样要 256 MB 可用内存才能启动。

设置页底部那行「当前可用内存 N MB · XX 预计需要 N MB（可启动/内存紧张/内存不足）」
就是这套判定的实时结果，数字每 2 秒刷新一次。

## 4. 配置方法

### 4.1 设置页（推荐）

**设置 → IDE 工作台 → 语义分析**：

| 控件 | 字段 | 说明 |
|---|---|---|
| 构建代码索引 | `lsp.enabled` | 总开关。关掉立即结束正在运行的索引进程并释放内存 |
| 打开未索引目录时 | `lsp.indexOnOpen` | `ask`（默认）/ `always` / `never` |
| **语言服务器内存上限 (MB)** | `lsp.memoryLimitMB` | **所有**语言的上限。调低它每个语言都变小；调高它**不能**突破某个语言自身的内置上限 |
| 保守兜底下限 (MB) | `lsp.freeMemoryThresholdMB` | 仅在**认不出语言**、没有估算时兜底 |
| 内存余量系数 | `lsp.memoryHeadroom` | 需求 = 估算 × 系数。默认 1.5 |
| 内存硬下限 (MB) | `lsp.memoryHardFloorMB` | 低于此值一律不启动。默认 256 |
| 空闲退出 (分钟) | `lsp.idleTimeoutMs` | 默认 10 分钟 |
| 请求超时 (毫秒) | `lsp.requestTimeoutMs` | 下限 30 秒，见 §6.5 |
| 每行的**上限 (MB)** | `lsp.servers[语言].memoryLimitMB` | 留空 = 用全局上限；填了会**替换**全局上限，可以更高 |
| 每行的开关 | `lsp.servers[语言].enabled` | 关掉某个语言，它就只使用基础模式 |

### 4.2 直接编辑设置文件

`$DSH_HOME/ide-workbench/settings.json`（默认 `~/.dsh/ide-workbench/settings.json`；
宿主导出 `DSH_PROFILE_DIR` 时用 profile 目录）：

```json
{
  "lsp": {
    "enabled": true,
    "indexOnOpen": "ask",
    "memoryLimitMB": 2048,
    "freeMemoryThresholdMB": 512,
    "memoryHeadroom": 1.5,
    "memoryHardFloorMB": 256,
    "idleTimeoutMs": 600000,
    "requestTimeoutMs": 30000,
    "cancelAfterMs": 60000,
    "autoExit": true,
    "autoRestart": true,
    "servers": {
      "typescript": {
        "enabled": true,
        "memoryLimitMB": 4096,
        "memoryBaselineMB": 512
      },
      "yaml": { "enabled": false }
    }
  }
}
```

按语言可用的键：

| 键 | 含义 | 界面可改？ |
|---|---|---|
| `enabled` | 是否启用这个语言 | ✅ |
| `command` / `args` | 换掉注册的命令与参数 | ❌ 仅文件 |
| `memoryLimitMB` | 这个语言的上限（**替换**全局上限） | ✅ |
| `memoryBaselineMB`（别名 `baselineMB`） | 这个语言的估算 | ❌ 仅文件 |
| `indexedRoots` / `memoryWarnedRoots` | 由工作台自己维护，一般不用手改 | ❌ |

改完保存即生效；正在运行的服务器要等下一次启动/重启才用上新值。

## 5. 已知局限

1. **全局上限只能往下调。** 生效值是 `min(内置上限, 全局上限)`。全局设 4096，
   TypeScript 仍然是 2048。要给某个语言更多，用它自己那一行的上限。
2. **只有 TypeScript 的服务器真的听这个上限。**
   `typescript-language-server` 支持 `maxTsServerMemory`，会真的限制自己的堆；
   其余（`jdtls` / `gopls` / `rust-analyzer` / `clangd` / `basedpyright` /
   `yaml-language-server`）只把这个数字当作**估算的封顶**，**不限制进程本身**。
   状态栏会注明哪些服务器不支持上限。
3. **估算是典型占用，不是最坏情况。** 大项目的真实占用远高于估算 —— TypeScript
   服务器要为整个项目建 program。估算只决定「要不要问你要不要启动」，**不决定
   「撑不撑得住」**。大项目请按语言把 `memoryBaselineMB` 调高。
4. **可用内存是启动那一刻的快照**，之后不再复测。机器上的其它程序随时可能吃掉内存，
   服务器也可能在运行中一路涨上去。
5. **首次语义请求可能要等十分钟。** 大项目建 program 实测可超过 10 分钟。在此之前
   请求预算给到 10 分钟，服务器回答过第一个**真实**请求（握手的 `initialize`
   毫秒级回答，不算）之后，才回到配置的 `requestTimeoutMs`（下限 30 秒）。
   副作用：**第一次补全弹窗可能长时间不返回** —— 那是在建索引，不是卡死；
   状态栏此时显示「语义分析：索引中…」。
6. **空闲十分钟后语言服务器退出**，内存回落；下次打开重建（通常更快，因为文件还在
   系统页缓存里）。
7. **Windows 上语言服务器的 CPU 优先级被调低**（低于正常），以免抢占 DSH agent
   的 CPU。这不影响内存上限。
8. **崩溃后只自动重启一次**（`autoRestart`），再崩就降级为基础版，由状态栏的诊断
   面板手动「重新建立索引」。

## 6. 排查

| 现象 | 多半是 |
|---|---|
| 状态栏一直「索引中…」 | 大项目建 program，等 §5.5 |
| 状态栏「不稳定」/ 弹「Request timed out」 | 请求预算问题，见 §5.5；也可把 `requestTimeoutMs` 调大 |
| 明明调大了内存上限却没变化 | §2：全局上限不能突破语言的内置上限，用按语言的上限 |
| 明明内存够却不启动 | 可用内存 < 硬下限；或可用内存落在「紧张」区间而用户在弹窗里选了基础模式 |
| 内存一直涨 | 估算是典型占用；按语言调高 `memoryBaselineMB`，或调低 `memoryLimitMB` |
| 想要一个绝对上限 | 只有 TypeScript 系列支持；其余服务器需要自己在 PATH 上包一层带内存限制的启动脚本 |

诊断面板（点状态栏 → 「诊断」）里有：最近一次失败、语言服务器的 stderr、以及同一份
实时内存快照。
