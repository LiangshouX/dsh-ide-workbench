## 0. 结论摘要

### 0.1 一句话结论

**DSH 今天没有「多窗口」契约，插件无法自行造出"第二个 DSH 窗口"；可行路径只有两条——Web 形态下由插件自服务一个同源独立页面（需要插件自己拼装启动协议），Desktop 形态下必须由宿主（Electron 主进程）新增窗口契约（`window.open` 在桌面端被显式 `deny`）。** 这不是一个纯前端功能，它是一次**宿主契约 + 插件架构**的双向改造。

> **修正（2026-11-20 晚，补查后）**：Desktop 形态**不是"从零做"**——桌面的多窗口骨架、启动注入、`boot` IPC、HTTP 承载四根管线**已经在**（§3.2 的表），缺的只有"开窗口的服务"+"第二窗口的 WS 承载"+"窗口身份"三个契约点。**"插件单方面做不到" ≠ "桌面端做不了"。**

### 0.2 五条关键判断

| # | 判断 | 依据强度 |
|---|---|---|
| 1 | **插件的客户端半边不是独立网页应用**：`apply(ctx)` 的全部能力来自宿主注入的 `ctx`（slots / locale / sidebarRight / sidebarRightTabs / sessions / modules）。任何"插件自己 serve 一个 HTML 页"的路线，**默认没有 `ctx`**，等于要自建一个最小宿主替身。 | 读码确认（`client/index.jsx:31,446-451,654-657`） |
| 2 | **宿主没有任何"独立窗口"扩展点**：`window.open` 全仓库仅 5 处、全是外链/OAuth 且都带 `noopener`；无 `BrowserWindow` 服务、无 BroadcastChannel/postMessage 契约、无 URL→Session 深链。 | 读码确认（全包 grep + `app.asar/lib/main.js`） |
| 3 | **Web 形态（`dsh web`）技术可行，但插件要自己拼启动协议**：启动图 `__DSH_BOOT__` 是**进程级全局**（无裁剪 API），插件页面只能启动**全量**客户端树；且页面 URL 必须在**站点根**（子路径会让客户端自身的相对路由与 workbench 的相对拼接双双错位）。 | 读码 + 实测确认 |
| 4 | **Desktop 形态（Electron）：插件单方面做不到，但宿主侧的管线大部分已经在**——主窗口 `setWindowOpenHandler` 一律 `deny`（http/https 交给 `shell.openExternal`），插件**无法自己开窗**；但桌面宿主**已经**在向 Electron 主进程下发 tokenized URL 与启动注入行（`dsh-desktop-host/lib/index.js:515,519`），`DESKTOP_IPC.boot`（`app.asar/lib/main.js:20809-20817`）对**任意 `dsh-app://app/` 渲染进程**都能起一个完整客户端。**真正缺的只有 3 个契约点**（§4.1），其中最硬的是"第二窗口的 WS 认证承载"——`onBeforeSendHeaders` 的 Cookie 改写被限定为主窗口（`:20832-20834`），第二窗口即使开出来也**没有活连接**。 | 读码确认（`app.asar/lib/main.js:20278-20281,20809-20817,20832-20854`；`dsh-desktop-host/lib/index.js:509-522`） |
| 5 | **跨会话的真问题不是"会话"，是"项目 + 进程级单例"**：宿主 `projectRoot` 是**进程级单变量**，两个窗口选不同项目会互相覆盖 `projectRoots[workspace]` 与 `lastRoot`，进而让 codeintel 的 LSP 作用域跟错；另外**编辑器草稿完全不持久化**，双窗口必然丢内容。 | 读码确认（`host/index.js:127,142-148`；`client/store.js:1356-1399`） |

### 0.3 推荐路线（分层，不是一刀切）

| 层级 | 形态 | 覆盖发行形态 | 是否需要宿主新增契约 | 建议 |
|---|---|---|---|---|
| **L0** | 侧栏内全屏 / 浮层 | 全部 | 否（已有 `toggleFullscreen`、宿主 `float`/`dock`） | **先做**：作为独立窗口的"退化档"，窗口不可用时也有体验 |
| **L1** | 同源新标签页 / popup，页面在**站点根** | Web | 少量（见 §4） | **可自证**：插件侧改造为主，宿主只需确认 3 条 |
| **L2** | 独立 OS 窗口（DSH 自己的窗口） | Desktop | **必须**（Electron 新窗口契约 + 第二窗口的连接承载） | **需上游排期**，但宿主侧管线大部分已就绪（见 §0.2 判断 4）；本插件先把 L1 做通，接口预留 |
| **L3** | 插件自建服务 + 自带前端（独立身份） | 全部 | 否（但要自担认证与安全） | **不建议**（见 §3.4 的四条理由） |

### 0.4 必须先决策的三件事（否则下面所有工作都是空转）

1. **"独立窗口"的语义**：是"浏览器新标签页/popup"（Web），还是"DSH 自己的 OS 窗口"（Desktop）？两者的宿主契约完全不同，且**不能同时用一条 `window.open` 实现**。
2. **窗口绑定什么**：**会话** / **工作区** / **项目**？本报告建议 **项目为主、会话为可选附件**（§5.1），这会决定后续所有状态归属。
3. **是否允许"第二个 DSH 客户端运行时"**：允许（第二窗口启动全量客户端）还是不允许（只能起一个裁剪版）。这一条决定宿主要不要新增"子图启动"能力，也是 L1/L2 路线的分水岭。

## 1. 需求界定：什么算"独立窗口"

同一句需求在产品上有四种截然不同的实现，代价差两个数量级。本报告先把它们分开：

| 层级 | 名称 | 含义 | 用户感知 | 跨窗口状态共享 |
|---|---|---|---|---|
| **L0** | 侧栏内全屏 | 右栏占满视口，宿主仍是同一个 document | 还是"侧栏里放大" | 无需处理 |
| **L0′** | 页内浮层 | 独立面板浮在页面上（宿主 `float` / 工作台自己的 `layout.floating`） | "弹出来一块" | 同 document，无问题 |
| **L1** | 同源新标签页 / popup | 浏览器新顶层上下文，**同源**，仍是 DSH 页面 | "另开了一个窗口/标签" | 需跨窗口协议 |
| **L2** | 独立 OS 窗口 | DSH 自己的原生窗口（Electron `BrowserWindow`） | "另开了一个 DSH" | 需跨窗口协议 + 宿主窗口契约 |
| **L3** | 插件自建 HTTP 服务 + 自带前端 | 另一套前端 + 另一套端口 | "另一个网页应用" | 需自建全部机制 |

> 本报告把 **L1 / L2** 视为本需求的正解，把 **L0 / L0′** 视为既有台阶与降级路径，把 **L3** 视为需要否决的备选（理由见 §3.4）。

**一个必须先说清的事实**：业界没有一家把"面板"做成"把 DOM 搬进另一个窗口"。VS Code 移动编辑器到新窗口时是**销毁旧 webview、在新窗口重建**（[webview 指南](https://code.visualstudio.com/api/extension-guides/webview)："The contents of webviews however are created when the webview becomes visible and destroyed when the webview is moved into the background"）。JetBrains 的 Window 模式是**同一个 IDE 进程里的另一个原生窗口**，共享同一 project model。**⇒ 独立窗口只能是"视图"，真源必须在宿主进程侧**——这是整份调研的主线。

## 3. 候选方案

### 3.1 方案 A —— 同源新标签页 / popup + 插件自服务独立页面（Web 形态）

**机制**
1. 宿主侧：插件注册 **exact 路由** `/`（或站点根的某个"视图参数"）的兄弟路径，返回自产 HTML；或者更稳妥：注册 `/ide-workbench/app`，但 HTML 里插 `<base href="/">`。
2. 该 HTML 用 `ctx.webServer.renderIndex(html, peer)` 过一遍，拿到宿主的启动注入行（`__DSH_BOOT__` + queue facade + bootstrap 脚本）⇒ 页面启动**全量 DSH 客户端**。
3. 客户端侧：工作台额外注册一个 **`main` keyed 面板**（`main[key='ide-workbench']`），在独立窗口里调用 `ctx.layout.selectPanel('ide-workbench')` ⇒ 窗口显示的是工作台整页，而不是会话界面。
   - 依据：本仓库 `docs/M0-api-findings.md:12` 早已确认 "`main` 是 keyed 整页容器，插件可在其中自绘编辑器区"；宿主侧 `ctx.layout.selectPanel(id)`（`dsh-client-ui-layout/src/client/service.ts:36,72-77`）。
4. 打开动作：`window.open(url, name, 'popup,width=1440,height=900')`，**必须在用户手势的同步调用栈里**（MDN：每次 `window.open` 需独立手势；被拦时返回 `null`）。

**需要的宿主契约**：只有 3 条"确认"级（§4 的 O1/O2/O3），不需要新增代码。

**优点**：不依赖宿主排期；同一套宿主 API/设置/PTY 全部复用；会话、审阅、聊天桥都能继续工作（同源 ⇒ cookie 与 origin 都对）。

**风险 / 代价**
| 风险 | 说明 | 缓解 |
|---|---|---|
| **启动全量客户端** | 第二窗口加载全部 client 包（chat、settings、plugins…），启动更重 | 接受；或推动宿主做子图启动（§4 C4） |
| **页面必须落在站点根** | DSH 客户端自身用相对路由（`api/...`），子路径下全部 404；workbench 的 `httpUrl`/`wsUrl` 同样相对拼接 | 页面 URL 用 `/?view=workbench`，或注入 `<base href="/">`；**并改 workbench 的 `api.js` 为 origin 基准绝对路径**（更稳） |
| **同源不等于同 Peer** | 两窗口共享 `browserPeer`，宿主无法按窗口授权 | 明确"独立窗口不获得额外权限"，并把它写进文档 |
| **弹窗被拦** | 每次 `window.open` 需手势；Chrome 默认开成新标签页 | 先同步 `window.open` 空窗再导航；被拦时给"在新标签页打开"的链接 |
| **插件页面被 SPA 吞掉** | fallback 席位已被 `frontend-static` 占用 | 用 **exact 路由**（匹配序 exact 先于 fallback），不是子路径 fallback |
| **合规** | `practices.md:33` 劝阻自出 HTML 页 | 见 §4 C10 |

### 3.2 方案 B —— 宿主新增"独立窗口 / 独立页面"契约（Desktop 形态必需）

**机制**：由宿主（`dsh-desktop-host` + Electron 主进程）提供"打开一个 DSH 窗口"的服务，例如 `ctx.window.open({ url, title, size })`，Electron 侧 `new BrowserWindow({ webPreferences:{ partition: <与主窗口相同>, sandbox: <与主窗口相同> }, ... })` 并 `outlivesOpener: true`（[Electron 文档](https://www.electronjs.org/docs/latest/api/window-open)：子窗口默认随 opener 关闭；`sandbox`/`contextIsolation` 与父窗口不一致会导致 `window.opener` 断裂）。

**需要的宿主契约**：C1（窗口语义）、C9（Electron 新窗口策略）、**C9b（第二窗口的连接承载）**、**C9c（窗口身份传递）**、C2（窗口→Session 选择）、C3（per-window Peer）、C8（跨窗口通信）。

**优点**：Desktop 形态能真正开"DSH 的第二个窗口"；与 JetBrains "Window 模式"、VS Code "Move into New Window" 的用户心智一致。

**代价**：宿主产品代码改动（`app.asar/lib/main.js` 的 Electron 主进程 + `dsh-desktop-host`），**不是插件能自己解决的**。

**但改动量比想象小（重要修正）**——桌面侧的四根管线**已经存在**：

| 管线 | 现状 | 证据 |
|---|---|---|
| 多窗口骨架 | `createWindow(preload, show, primary)` 已存在，多开一个只是多调一次 | `app.asar/lib/main.js:20242-20277` |
| 启动注入 | 桌面宿主已把 `collectIndexInjections(browserPeer)` 发给主进程 | `dsh-desktop-host/lib/index.js:519` |
| boot 通道 | `DESKTOP_IPC.boot` 对**任意 app 帧**返回 `{injections, streamBaseUrl}` | `app.asar/lib/main.js:20809-20817` |
| HTTP 承载 | `dsh-app://app/<非 dist 路径>` → 转发给后台 Host（换 Host + 注入 Cookie）⇒ 插件路由可达 | `app.asar/lib/main.js:20791-20797,15348-15379` |

⇒ 桌面端真正要补的是：**① 一个"开窗口"的服务（C9）；② 把 WS 认证承载从"主窗口"放宽到"所有 app 帧"（C9b，一行判断的改动量）；③ 窗口身份与选择（C9c/C2）**。第二窗口的客户端启动、HTTP 通信都已经通了。

**折中出口（不碰 Electron）**：桌面端 `window.open` 会把 http/https 交给系统浏览器（`shell.openExternal`）⇒ 可以让用户"在浏览器里打开工作台"。但浏览器里**没有 DSH 的认证 Cookie**（桌面壳会主动清掉 `dsh-auth-*`，`app.asar/lib/main.js:15313-15315`），必须走 token 登录流，而 **token 目前只认 `GET /`**（`browser-auth.ts:269`）⇒ 需要 C7。好消息是**桌面宿主已经算出了 tokenized URL**（`dsh-desktop-host/lib/index.js:515`），只要把它暴露给用户、并让 token 交换能落到插件路径上，这条路就通。

### 3.3 方案 C —— 插件自建 HTTP 服务 + 自带前端

**机制**：插件在宿主进程里 `node:http.createServer()` 监听 `127.0.0.1:<随机端口>`，自带一个前端 bundle，与宿主只通过 `/ide-workbench/api/*` 通信。

**否决理由**
1. **安全责任全落在插件**：宿主的围栏（Host/Origin + 签名 Cookie）不会覆盖这个端口。插件必须自己实现 Origin 校验 + 一次性 token，否则**任意网页都能打开这个本地端口读用户的源码**（这是实打实的 CSRF/数据泄露面）。
2. **丢掉整个 DSH 客户端**：没有 `ctx` ⇒ 没有 slots / locale / sessions / modules 原语 / 主题令牌；工作台的四个 `scope:'session'` 子插槽全部失效 ⇒ codeintel 的语义功能整体消失。
3. **契约分裂**：客户端契约（`packages/contract`）是 core↔codeintel 的通道；自带前端意味着 codeintel 要再出一份前端包，破坏 PRD-v6 的"一个契约、两个插件"结构。
4. **发行形态差异**：Desktop 下页面 origin 是 `dsh-app://app/`，插件自建服务在桌面端反而更绕。

### 3.4 方案 D —— 不新开窗口（整页 / 浮层降级档）

- `main` 整页面板（宿主 `ctx.layout.selectPanel`）—— **同一窗口内**的"整个工作台"。
- 宿主 `float` 浮动面板 —— 脱离停靠格。
- 工作台自带的 `layout.floating` 浮动工具窗。

**定位**：作为 L1/L2 不可用时的降级档与统一交互（同一个"独立"按钮，在能开窗时开窗，不能时退化为整页）。同时它是**唯一零契约成本**的一档，建议第一阶段先落。

### 3.5 方案 E —— 交给外部 IDE（已有，不动）

`openInIde`（IDEA / WebStorm / VS Code，`--new-window`）已经是"把整个项目交给另一个进程"的成熟范式。可作为"用户就是要真正独立的开发窗口"的答案，但它是**另一款软件**，不满足"DSH 工作台脱离侧边栏"的诉求，只适合作为文案里的备选说明。

### 3.6 横向对比

| 维度 | A：同源 popup（Web） | B：宿主新窗口（Desktop） | C：自建服务 | D：同窗整页 | E：外部 IDE |
|---|---|---|---|---|---|
| 宿主改动 | 0（3 条确认） | **大**（Electron 主进程 + 新服务） | 0 | 0 | 0 |
| 插件改动 | 中（页面 + `main` 面板 + API 基准） | 中（同 A） | **大**（自带前端） | 小 | 0 |
| 复用 DSH 客户端能力 | ✅ 全量 | ✅ 全量 | ❌ | ✅ | ❌ |
| 真·独立 OS 窗口 | ❌（浏览器决定） | ✅ | ❌ | ❌ | ✅ |
| 跨窗口状态共享成本 | 中（需协议） | 中（需协议） | 高 | **无** | 无 |

## 5. 跨会话与多窗口状态

### 5.1 窗口绑定什么：三种语义与建议

| 语义 | 窗口的身份 | 优点 | 缺点 |
|---|---|---|---|
| **窗口 = 会话** | 绑定一个 DSH Session | 与现有模型一致；聊天/审阅天然可用 | 一个会话只能有一个窗口；会话结束窗口就废；会话切换时窗口要跟着换内容 |
| **窗口 = 工作区** | 绑定一个 workspace（cwd） | 与 store 作用域键一致（`workspaceScopeKey`） | 同一工作区两个会话仍会争 `projectRoot` |
| **窗口 = 项目**（建议） | 绑定一个 **项目根**（`projectRoots[workspace]`），会话是**可选附件** | 与 IDE 心智一致（JetBrains/VS Code 都是项目为中心）；跨会话功能（聊天/审阅）按需挂载，缺失时优雅降级 | 需要新增"窗口→项目根"的绑定与持久化 |

**建议：窗口 = 项目根为主键，会话为可选附件。**
理由：① 宿主侧已有 `projectRoots[workspace]` 这张表（`host/settings-store.js:170`），天然可作为窗口身份；② 工作台的数据模型本来就是项目中心（`workspaceState[projectRoot]`、`projectRoot`、`HOST_SERVICE.getProjectRoot()`）；③ IDE 行业惯例一致；④ 会话相关功能（@file 发送、turn 审阅、链接 claim）可以在"窗口没有会话"时明确降级，而不是让整个窗口不可用。

### 5.2 绑定矩阵（工作台侧，逐条已读码确认）

### 5.4 「同一文件两个窗口」的仲裁（必须显式设计）

VS Code 的硬约束是 "A webview panel may only show in a single editor column at a time"；JetBrains 也规定一个 tool window 同时只有一种 view mode。**本项目需要一条等价规则**，否则双窗口编辑同一文件必然互相覆盖：

- 候选规则：**"一个文件在一个时刻只属于一个窗口"**——第二个窗口打开同一文件时，变为只读并提示"该文件已在窗口 X 编辑"。
- 需要的支撑：宿主侧知道"文件 → 窗口"的占用（今天的 `terminals` Map 是进程级的，可以照此模式做一张 `fileOwners` 表），以及窗口生命周期事件（现在**没有**，窗口关闭宿主不知道 ⇒ C3/C12）。
- 若不做这条规则，**至少**要有草稿的 last-writer-wins 提示与冲突提示，否则是静默丢数据。

## 6. 安全与信任边界

| # | 议题 | 事实 | 结论 / 要求 |
|---|---|---|---|
| S1 | 同源弹窗的认证 | 签名 Cookie `SameSite=Strict` 对**同站**新窗口不拦截；围栏要求 Origin 同 authority + Host loopback ⇒ **同源 popup 天然过围栏** | 可行，但不要把"能用"当成"安全"：独立窗口与主窗口**权限完全相同** |
| S2 | 系统浏览器 / 别的 profile 打开 | 无 Cookie ⇒ 401，且提示是 `dsh web authentication required; reopen the URL printed by dsh web.`（与插件无关，**极易误判为插件 bug**） | 要么走 token（但 token 只认 `GET /`，C7），要么引导用户用 DSH 内置入口 |
| S3 | 跨源弹窗 | `SameSite=Strict` 下跨站导航不带 Cookie；`Lax` 仅顶层 GET 导航带，**`fetch`/XHR 一律不带** | **禁止**跨源方案；DSH 固定单一 canonical origin（不要混用 `localhost` 与 `127.0.0.1`） |
| S4 | `window.open` 的 opener | DSH 内所有 `window.open` 都带 `noopener,noreferrer` ⇒ `window.opener` 不可用；COOP 会进一步切断引用 | 跨窗口通信只能用 **BroadcastChannel（同源）** 或**宿主事件流**，不能依赖 opener |
| S5 | `sessionStorage` | 按 tab + origin 分区，关标签即销毁 | 跨窗口共享一律用 `localStorage`（同源共享）或宿主 |
| S6 | 插件自建端口（方案 C） | 绕过 Host/Origin 栅栏 ⇒ 任意网页可读用户源码 | **否决方案 C**；若坚持，必须自建 Origin 校验 + 一次性 token + 绑定 loopback |
| S7 | `readResource` 是"无检查读" | `dsh-host-webserver/src/index.ts:488-510` 明说不做 cookie/Host/Origin 检查 | 不要用它"抄"宿主 index 来拼启动协议（依赖内部实现，宿主一改就碎） |
| S8 | CSP | 应用 index 无 CSP ⇒ 页面可注入内联脚本；但插件若给自己的页面加 `sandbox; default-src 'none'` 会把自己的脚本也禁掉 | 独立页面用 **外链 script + `<script type="application/json">` 数据岛**，避免内联引导 |
| S9 | 相对寻址导致的静默 404 | 客户端 `api/...` 与 workbench `httpUrl/wsUrl` 都是相对拼接 | 页面放站点根；并把 workbench 的 API 基准改成 **origin 绝对路径**（消除一整类隐患） |
| S10 | `SameSite=Strict` + `HttpOnly` | 不能靠 Cookie 传跨窗口信道标识 | 信道标识走 URL 参数 + BroadcastChannel name |

## 8. 业界先例与对本项目的启示

| 产品 | 做法 | 关键点 | 对 DSH 的启示 |
|---|---|---|---|
| **VS Code** | 浮动/辅助窗口（`Move/Copy into New Window`）、Agents 窗口（`Chat: Open Agents Window`，并支持 **"Move to Main Window" 回迁**） | ① 新窗口**共享**工作区模型与 buffer，**不共享**扩展宿主；② 为让两窗共享 Agent 会话，专门做了**与窗口无关的 Agent Host 进程 + 订阅式协议**；③ webview 移窗是"销毁重建"不是"搬 DOM"；④ **一个编辑器只在一个窗口** | ① 独立窗口只是**视图**，真源必须在宿主进程；② 需要一条**跨窗口订阅协议**；③ 必须有"回迁"；④ 需要"文件唯一归属"规则 |
| **VS Code for the Web** | 没有真独立窗口，"新窗口"就是**新标签页**；弹窗需用户授权 | Web 形态下"独立窗口"的天花板 | DSH 的 Web 形态应如实定义为"独立标签页/popup"，不要承诺 OS 窗口体验 |
| **JetBrains IDE** | 工具窗口五种视图模式：Dock Pinned / Dock Unpinned / Undock / **Float** / **Window**；**Window 模式 = 真正的独立原生窗口**，可移到别的显示器；布局可存为 Layout；Terminal/Git/Project **都是 tool window**，都能脱窗 | Float 依赖主窗口存活，只有 Window 才独立 | ① DSH 的四个工具窗应统一支持"脱窗"；② **Float 与 Window 要分档**；③ 布局可持久化 |
| **Chrome DevTools** | `Undock into separate window` —— 脱窗后 DevTools 前端本身是一个 web 应用（`devtools://` 源），与被调试页共享同一 profile/session | 同一浏览器 session、同一 cookie，换一个顶层窗口渲染 | 与 DSH 方案 A（同源 popup）语义高度相似，是最贴近的浏览器内先例 |
| **Zed / Helix / Sublime** | 尚无"面板脱窗"能力（Zed 社区 #47116 仍是开放诉求） | —— | 本方向有差异化价值，但说明**没有现成范式可抄**，必须自己定义跨窗口模型 |

**三条通用结论**
1. **二级形态 + 可逆**：侧栏是默认形态，独立窗口是"逃生舱"，必须能收回（VS Code 有 "Move to Main Window"；JetBrains 随时改 View Mode）。
2. **状态在宿主、窗口是渲染器**：VS Code 为此专门抽出了 Agent Host 进程；JetBrains 共享 project model。⇒ DSH 若把会话/草稿/终端放在页面 JS 内存里，拆窗必丢状态。
3. **浏览器形态与 Electron 形态要分叉实现，但共用同一份工作台 bundle**。

### 12.4 术语约定

| 术语 | 本报告含义 |
|---|---|
| 宿主 / Host | DSH 进程（含 `dsh-host-webserver`、`dsh-client-connection` 的宿主面） |
| 客户端 / Client | 浏览器侧的 DSH 前端（由宿主注入 `window.__DSH_BOOT__` 引导） |
| 插件两半 | `dsh-ide-workbench` 的宿主半边（Node）与客户端半边（浏览器） |
| 表面 / surface | 一个"工作台实例的呈现位置"（右栏页签 / 整页面板 / 独立窗口） |
| Peer | 宿主侧的主体对象（`PeerScope`），承载 principal 与事件参与权 |
| 围栏 / fence | `ctx.connection.requestRejection(req)`：Host/Origin 栅栏 + 浏览器认证 |
