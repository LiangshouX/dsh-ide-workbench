# 代码索引的内存配置：含义、配置方法与已知局限

> **面向对象**：使用 IDE 工作台、并且关心「语义分析要吃多少内存」的人。
> **一句话**：索引占的内存由**语言服务器进程**决定，工作台只能**估算**它；估算值
> 决定「要不要启动 / 要不要问你」，**上限**决定「它最多能长到多大、机器要替它留多少」，
> 而**只有一种服务器真的按这个上限限制自己**。
> 规格见 `docs/prd/v5/PRD-v5-补充需求.md`（§2.2 / §2.3 / §4.4）与
> `docs/prd/v5.1/PRD-v5.1.md`（§3 内存闸门重算 / §4 并发索引策略），本文件是**面向使用者的说明**。

---

## 1. 三组数字，含义完全不同

最常见的误解是把「上限」和「估算」当成一回事。它们是两个独立的数；V5.1 又加了第三个：
**实测占用**。

| | 字段 | 含义 | 谁在用 |
|---|---|---|---|
| **上限** | `lsp.memoryLimitMB`（全局上限）<br>`lsp.servers[语言].memoryLimitMB`（按语言，替换全局） | 交给语言服务器的**内存天花板** | ① 作为启动前估算的封顶；② **只有 TypeScript** 真的把它传给服务器进程；③ 作为「机器要替它留多少」的记账单位 |
| **估算** | `lsp.servers[语言].memoryBaselineMB`（按语言） | 这类语言服务器的**典型占用**（不是最坏情况） | 只用来和「当前可用内存」比，算出要不要启动 |
| **实测占用** | 不可配置（宿主自动测量） | 这台服务器**现在真的占了**多少 | 决定「它还可能再涨多少」，也就是记账里的预留额 |

**内置估算**（MB，未配置时的默认）：

| 语言 | 估算 | 内置上限（分档前） |
|---|---|---|
| TypeScript / JavaScript | 434 | 2048 |
| Java | 512 | 2048 |
| Rust | 512 | 2048 |
| C / C++ | 384 | 2048 |
| Go | 256 | 1536 |
| Python | 192 | 1536 |
| YAML | 64 | 512 |
| 未知语言 | 256 | — |

## 2. 生效上限是怎么算出来的（V5.1 起按项目规模分档）

```
生效上限 = 按语言设置的上限                       （它「替换」其它一切，可以更高）
          或 min(按项目规模的分档, 该语言的内置上限, 全局上限)
```

**分档**（`PRD-v5.1` MEM-11）—— 按项目的**源码文件数**（有界扫描，不遍历整棵树）：

| 项目规模 | 源码文件数 | 分档上限 |
|---|---|---|
| 小 | ≤ 400 | 1024 MB |
| 中 | ≤ 1000 | 1536 MB |
| 大 | > 1000 | 2048 MB |
| **规模未知**（目录不存在 / 读不到 / 没有源码） | — | **2048 MB**（保持内置上限） |

> **「规模未知」保持大项目的上限**，因为「数不出文件」不等于「项目小」：把上限压下去
> 却不知道为什么，正是大项目建不起索引的原因。真要更多，用按语言的上限覆盖。

所以：

- **调低全局上限 → 每个语言都跟着变低**（取更小的那个）。
- **调高全局上限 → 对内置上限更高的语言无效**。全局设成 4096，TypeScript 仍然是
  2048 —— 因为它的内置上限就是 2048。
- **要给某一个语言更多 → 用它自己那一行的上限**。按语言的设置是**替换**，不是叠加，
  所以它可以比全局上限更高。
- **小项目会自动拿到更小的上限**（1024 MB），大项目仍是 2048 MB。

> 这一点在 2026-10-31 的第二轮检视中被反复反馈（「看着还是像 2048」）：全局值调上去了
> 却看不到变化。设置页的提示文案现在写明了这层关系。

## 3. 四道闸门：能不能启动

启动（或崩溃后重启）那一刻，宿主读一次机器的**可用内存**，和估算比：

```
每个运行中的服务器 i：
  上限_i   = 它被授予的上限（§2）
  实测_i   = 它现在真的占了多少（宿主用 os.freemem() 的差值自动测量）
  还能涨_i = max(0, 上限_i − 实测_i)          ← 它「还可能再吃」多少

可用内存 = 整机空闲内存 − Σ 还能涨_i

需求 MB = min(估算, 生效上限) × 内存余量系数(默认 1.5)
软阈值  = 需求 MB × 2
```

| 可用内存 | 判定 | 行为 |
|---|---|---|
| `≥ 软阈值` | **可启动** | 直接启动语言服务器 |
| `硬下限 ≤ 可用 < 软阈值` | **内存紧张** | **弹窗问用户**：「仍然启动」或「使用基础模式」 |
| `< 硬下限`（默认 256 MB） | **内存不足** | 直接降级为基础模式，不启动 |

**为什么不再按「上限」记账**：V5.1 之前，宿主把每台运行中的服务器按**上限**扣一次。
可整机的空闲内存**已经扣过**它们真实占用的那份 —— 于是同一台服务器被记了两次账
（一次作为已消耗，一次作为上限）。这就是「机器还剩 2648 MB、索引只要 621 MB，
却被判定为资源不足」的根因。现在只扣**它还能再涨的那部分**。

两点补充：

- **硬地板是兜底，也是地板**：小语言也会被它托住。例如 YAML 的需求只有 96 MB，但
  硬下限 256 MB 更高，所以它同样要 256 MB 可用内存才能启动。
- **「保守兜底下限」（默认 512 MB）只在语言未知时生效**。有估算时用的是估算值，
  这个数字不参与判定 —— 它是「连语言都认不出来」时的保守值。

### 3.1 整机预算（MEM-08）：第四道闸门

前一道闸门管的是「下一台服务器能不能起」，管不了「三台服务器**同时**长到上限」。
所以还有一道**整机预算**：

```
预算 = min(整机内存 × budgetRatio(默认 0.25), budgetCapMB(默认 4096))
已用 = Σ 运行中服务器的上限

已用 + 本台上限 > 预算  ⇒  拒绝（**「仍然启动」也不能绕过**）
```

> 「仍然启动」回答的是「内存紧张时能不能开这一台」，**不是**「能不能突破整机预算」。
> 预算用完时，唯一出路是释放一台服务器，或在设置里调高预算。

另外还有一个可选的并发上限 `maxConcurrentIndexes`（默认 0 = 不限制，由预算决定）；
它与预算**同时生效时取更严者**。

### 3.2 最坏情况：如实报出来，不因此拒绝

诊断面板会同时给出两行：

```
典型：可用 1206 MB · 需要 651 MB
最坏：若该服务器吃到上限 2048 MB，机器将剩 −842 MB
```

**最坏档不会导致拒绝** —— 按 2 GB 上限算，几乎任何机器都会命中最坏档，硬拒等于把
闸门彻底封死。真正拦住内存耗尽的是**整机预算**与**压力释放阀**，不是这一行提示。

### 3.3 压力释放阀（MEM-12）：默认开启

机器真的紧张时（**可用内存**低于硬地板），宿主会**释放最不活跃的那台服务器**，
状态变成灰色「已让出内存」—— 这是**主动回收**，不是故障，下次语义请求会自动唤醒它。

- 压力定时器**默认就装**，与「空闲策略」无关；
- 空闲策略选「永不退出」**不豁免**压力释放（「永不退出」指「不因闲置退出」）；
- 唯一能关掉它的是设置里的 **`lsp.pressureYield`（默认开）**。

## 4. 配置方法

### 4.1 设置页（推荐）

**设置 → IDE 工作台 → 语义分析**：

| 控件 | 字段 | 说明 |
|---|---|---|
| 构建代码索引 | `lsp.enabled` | 总开关。关掉立即结束正在运行的索引进程并释放内存 |
| 打开未索引目录时 | `lsp.indexOnOpen` | `ask`（默认）/ `always` / `never`。**注意**：某个项目若被明确选过基础模式，它**不**受这里的 `always` 影响 |
| **语言服务器内存上限 (MB)** | `lsp.memoryLimitMB` | 所有语言上限的**全局上限**。调低它每个语言都变小；调高它**不能**突破某个语言自身的内置上限 |
| 保守兜底下限 (MB) | `lsp.freeMemoryThresholdMB` | 仅在**认不出语言**、没有估算时兜底 |
| 内存余量系数 | `lsp.memoryHeadroom` | 需求 = 估算 × 系数。默认 1.5 |
| 内存硬下限 (MB) | `lsp.memoryHardFloorMB` | 低于此值一律不启动。默认 256 |
| **整机预算** | `lsp.budgetRatio` | 语言服务器合计可占用的内存比例。默认 0.25 |
| **预算上限 (MB)** | `lsp.budgetCapMB` | 整机预算的绝对上限。默认 4096 |
| **同时建立的索引** | `lsp.maxConcurrentIndexes` | 你自己的并发上限。0 = 由预算决定 |
| **内存紧张时释放** | `lsp.pressureYield` | 压力释放阀的开关。默认开 |
| 空闲退出 (分钟) | `lsp.idleTimeoutMs` | 默认 10 分钟 |
| **空闲策略** | `lsp.idlePolicy` | `never` / `after`（默认）/ `onMemoryPressure` / `always` |
| 请求超时 (毫秒) | `lsp.requestTimeoutMs` | 下限 30 秒，见 §6.5 |
| 每行的**上限 (MB)** | `lsp.servers[语言].memoryLimitMB` | 留空 = 用分档值；填了会**替换**分档值，可以更高 |
| 每行的开关 | `lsp.servers[语言].enabled` | 关掉某个语言，它就只使用基础模式 |

### 4.2 直接编辑设置文件

`$DSH_HOME/ide-workbench/settings.json`（默认 `~/.dsh/ide-workbench/settings.json`；
宿主导出 `DSH_PROFILE_DIR` 时用 profile 目录）：

```json
{
  "lsp": {
    "enabled": true,
    "indexOnOpen": "ask",
    "memoryLimitMB": 2048,
    "freeMemoryThresholdMB": 512,
    "memoryHeadroom": 1.5,
    "memoryHardFloorMB": 256,
    "budgetRatio": 0.25,
    "budgetCapMB": 4096,
    "maxConcurrentIndexes": 0,
    "pressureYield": true,
    "idleTimeoutMs": 600000,
    "idlePolicy": "after",
    "requestTimeoutMs": 30000,
    "cancelAfterMs": 60000,
    "autoExit": true,
    "autoRestart": true,
    "servers": {
      "typescript": {
        "enabled": true,
        "memoryLimitMB": 4096,
        "memoryBaselineMB": 512
      },
      "yaml": { "enabled": false }
    }
  }
}
```

按语言可用的键：

| 键 | 含义 | 界面可改？ |
|---|---|---|
| `enabled` | 是否启用这个语言 | ✅ |
| `command` / `args` | 换掉注册的命令与参数 | ❌ 仅文件 |
| `memoryLimitMB` | 这个语言的上限（**替换**分档值与全局上限） | ✅ |
| `memoryBaselineMB`（别名 `baselineMB`） | 这个语言的估算 | ❌ 仅文件 |
| `indexedRoots` / `memoryWarnedRoots` / `workspaceDefaults` | 由工作台自己维护，一般不用手改 | ❌ |

> `workspaceDefaults` 记的是**每个项目的语义分析决定**（`build` / `conservative`），
> 它**优先于** `indexOnOpen`：你为一个项目选过基础模式，它就一直是基础模式，
> 即便全局策略是「总是索引」。

改完保存即生效；正在运行的服务器要等下一次启动/重启才用上新值。

## 5. 已知局限

1. **全局上限只能往下调。** 生效值是 `min(分档值, 内置上限, 全局上限)`。全局设 4096，
   TypeScript 仍然是 2048。要给某个语言更多，用它自己那一行的上限。
2. **只有 TypeScript 的服务器真的听这个上限。**
   `typescript-language-server` 支持 `maxTsServerMemory`，会真的限制自己的堆；
   其余（`jdtls` / `gopls` / `rust-analyzer` / `clangd` / `basedpyright` /
   `yaml-language-server`）只把这个数字当作**估算的封顶**，**不限制进程本身**。
   状态栏会注明哪些服务器不支持上限。
3. **估算是典型占用，不是最坏情况。** 大项目的真实占用远高于估算 —— TypeScript
   服务器要为整个项目建 program。估算只决定「要不要问你要不要启动」，**不决定
   「撑不撑得住」**。大项目请按语言把 `memoryBaselineMB` 调高。
4. **实测占用是差值测出来的，有噪声。** 宿主用服务器启动前后的 `os.freemem()` 差值
   测量占用；差值落在噪声区间（−64 MB ~ +8 MB）时测量作废，退回该语言的**估算值**，
   并在一分钟后复测。机器上同时有别的程序在抢内存时，账目会偏保守（而不是偏乐观）。
5. **可用内存是启动那一刻的快照**，之后不再复测。机器上的其它程序随时可能吃掉内存，
   服务器也可能在运行中一路涨上去。**压力释放阀**（§3.3）是这件事的兜底。
6. **首次语义请求可能要等十分钟。** 大项目建 program 实测可超过 10 分钟。在此之前
   请求预算给到 10 分钟，服务器回答过第一个**真实**请求（握手的 `initialize`
   毫秒级回答，不算）之后，才回到配置的 `requestTimeoutMs`（下限 30 秒）。
   副作用：**第一次补全弹窗可能长时间不返回** —— 那是在建索引，不是卡死；
   状态栏此时显示「语义分析：索引中…」。
7. **空闲十分钟后语言服务器退出**，内存回落；下次打开重建（通常更快，因为文件还在
   系统页缓存里）。被压力释放阀放掉的服务器也一样：下次语义请求会自动唤醒它。
8. **Windows 上语言服务器的 CPU 优先级被调低**（低于正常），以免抢占 DSH agent
   的 CPU。这不影响内存上限。
9. **崩溃后只自动重启一次**（`autoRestart`），再崩就降级为基础版，由状态栏的诊断
   面板手动「重新建立索引」。
10. **「仍然启动」只对当次生效。** 点过一次之后，同一个项目再次遇到内存紧张时
    **会重新问你** —— 「允许强启」不会被永久记住，也不会传染到别的项目。

## 6. 排查

| 现象 | 多半是 |
|---|---|
| 状态栏一直「索引中…」 | 大项目建 program，等 §6.5 |
| 状态栏「不稳定」/ 弹「Request timed out」 | 请求预算问题，见 §6.5；也可把 `requestTimeoutMs` 调大 |
| 明明调大了内存上限却没变化 | §2：全局上限不能突破语言的内置上限，用按语言的上限 |
| 明明内存够却不启动 | 可用内存 < 硬下限；或可用内存落在「紧张」区间而用户在弹窗里选了基础模式 |
| 明明内存够却被拒，提示「预算已用完」 | §3.1：整机预算用完了，释放一台服务器或调高 `budgetCapMB` |
| 内存一直涨 | 估算是典型占用；按语言调高 `memoryBaselineMB`，或调低 `memoryLimitMB` |
| 想要一个绝对上限 | 只有 TypeScript 系列支持；其余服务器需要自己在 PATH 上包一层带内存限制的启动脚本 |

诊断面板（点状态栏 → 「诊断」）里有：最近一次失败、语言服务器的 stderr、同一份
实时内存快照（**典型**与**最坏**两行），以及整机预算的已用额。
