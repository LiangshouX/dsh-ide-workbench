# 状态刷新事件化 —— 性能审计与修复（PRD-v8）

> 规格本体 `PRD-v8.md` **未改动**（AGENTS.md §6：规格与实施记录分开）。
> 本文件记录 2026-11-21 的一次**性能审计**：插件的宿主半边跑在 **DSH 的宿主进程**里，
> 所以插件在宿主里做的每一毫秒都是 DSH 自己的毫秒。本轮把「每 2 秒问一次 git」
> 换成「文件系统告诉我们要不要问」。
> 每条结论都标注 **[读码确认] / [实测确认] / [推断]**。

---

## 0. 诉求与结论

> 插件本身的流畅度、宿主 DSH 的流畅度是必须要保证的（卡顿决不能是由于我们的插件引起）。

| # | 怀疑 | 结论 |
|---|---|---|
| 1 | 每 2 秒的 `git.status` 轮询是宿主的主要负担 | **确认**。一次轮询 = 2～4 个 git 子进程 ≈ 250～640 ms，**每 2 秒一次** [实测确认] |
| 2 | 负担来自「未跟踪文件太多」 | **推翻**。`--untracked-files=no` 一样贵；成本是 **git 进程启动**（本机 ≈ 100～140 ms/次）[实测确认] |
| 3 | 快照太大，浏览器每 2 秒解析一次 | **确认**。20 000 个未跟踪文件时，一次快照是 **2.41 MiB** 的 JSON，浏览器解析 **18.6 ms**（> 16.7 ms 的一帧）[实测确认] |
| 4 | 每次轮询都重建整个工作台 | **确认**。`statusAt: Date.now()` 每次都是新值 → `set()` 变了 → 所有订阅者被唤醒 [读码确认] |
| 5 | `fs.watch` 在 Windows 上不可靠 / 更贵 | **推翻**。建立 **1.5～2.1 ms**（6 万文件）、空闲 **0 ms CPU / 5 s**、漏事件 **0/100**、延迟中位数 **3 ms** [实测确认] |
| 6 | 样式表会改写宿主的样式 | **部分确认**。793 条选择器里 **4 条**没有作用域，直接命中宿主的 CodeMirror [实测确认] |

## 1. 架构前提（这是整轮审计的地基）[读码确认]

- 插件的宿主半边是 **Cordis fiber**（`src/index.js` 的 `apply(ctx)`），它**跑在 DSH 的宿主进程里**，
  它的路由由 **DSH 自己的 web server** 提供服务（`ctx.webServer.register`）。
  → **宿主侧每一条 `git` 子进程、每一次目录遍历，都是 DSH 自己进程里的 CPU。**
- 插件的客户端半边是**注册进 DSH 页面的一个 bundle**（`src/client/index.jsx` 的 `apply(ctx)`）。
  → 客户端的一个长任务 / 一次渲染风暴会**卡住 DSH 的整个 UI**，不只是工作台。

这两条是「卡顿不能由我们引起」这句话的物理基础，也是本轮所有取舍的判据。

## 2. 实测（2026-11-21，Windows，Node v22.22.2，git 2.x）

### 2.1 一次轮询的代价

宿主路由 `git.status`（`src/index.js`）每次请求依次跑：

1. `git rev-parse --show-toplevel`（`repoEnv` → `repoRootOf`，`src/host/git.js:202`）
2. `git status --porcelain=v2 --branch -z --untracked-files=all --ignored=matching`
3. （仅 Commit 窗口可见时）`git diff --numstat -z` + `git diff --cached --numstat -z`

命令：`node qa-sandbox/perf/measure-git.mjs <repo> 5`（中位数，ms）

| 仓库 | 文件数 | `rev-parse` | `status` | **一次轮询（2 进程）** | **+numstat（4 进程）** |
|---|---|---|---|---|---|
| `dsh-ide-workbench`（真实） | 471 | 116 | 138 | **254** | **538** |
| 合成 1k | 1 000 | 138 | 139 | **277** | **502** |
| 合成 20k | 20 000 | 100 | 129 | **229** | **502** |
| 合成 60k | 60 000 | 112 | 206 | **319** | **637** |
| 合成 20k + 20k 未跟踪 | 40 000 | 126 | **235** | **361** | **677** |

**读法**：`git ls-files -z`（几乎不做事，只读索引）在本机就要 **106～127 ms** ——
**一个 git 子进程的固定成本约 100～140 ms**。工作树的比对只占剩下的部分
（471 文件 +22 ms，6 万文件 +94 ms）。 [实测确认]

⇒ **真正的成本是「每 2 秒在 DSH 宿主进程里创建 1～3 个 git 子进程」**，
而不是某一条命令慢。延长轮询间隔只是治标。

### 2.2 快照的体积（宿主 → 浏览器）

命令：`node qa-sandbox/perf/measure-status-payload.mjs <repo>`（直接调用 `src/host/git.js` 的 `status()`）

| 仓库 | 条目数 | 响应体 | 浏览器 `JSON.parse` |
|---|---|---|---|
| `dsh-ide-workbench` | 12 | 2.1 KB | 0.1 ms |
| 20k 跟踪 + 20k 未跟踪 | **20 000** | **2.41 MiB** | **18.6 ms** |

`sameGitStatus`（`src/client/store.js:132`）只挡住了**重渲染**，
**没有挡住传输与解析**：浏览器每 2 秒要在主线程上解析 2.41 MiB 的 JSON，
**18.6 ms > 16.7 ms（���帧预算）**。 [实测确认]

### 2.3 `fs.watch` 在 Windows 上可用吗

命令：`node qa-sandbox/perf/measure-watch*.mjs <repo>`（Node v22.22.2，Windows）

| 指标 | 6 万文件的仓库 | 2 万文件的仓库 |
|---|---|---|
| 建立耗时 | **1.5 ms** | 2.1 ms |
| 空闲 5 秒的 CPU | **0 ms（0% 单核）** | 0 ms |
| 单次深层修改的漏事件 | **0 / 100** | 0 / 100 |
| 事件延迟 | 中位数 **3 ms**，p95 5 ms，最大 9 ms | 同量级 |
| 新建目录后的写入 | **能看见**（3 个事件） | 能看见 |
| 删除 / 重命名 / 批量 4000 次写入 | 都能看见 | 能看见 |

**6 万文件的树上的 60 次修改只报 2 个事件**（Windows 侧做了合并）——
但工作台只需要知道「有东西变了」，不需要知道是哪一个文件。 [实测确认]

**反馈环的风险已排除**：`git status` **不写任何文件**（实测：真实仓库 10 490 个文件、
6 万文件仓库 60 278 个文件，跑 3～5 次 `git status` 后 **0 个文件的大小/mtime 变化**），
而且 `GIT_OPTIONAL_LOCKS=0` 已经在 `runGit` 里设了。 [实测确认]

## 3. 改动

### 3.1 宿主：`src/host/status-cache.js`（新增）

- **每个仓库根一个条目**：`{ revision, at, changes, seen, watched, watcher, root, options }`。
- **`fs.watch(root, { recursive: true })`**：变化只把 `changes` 加一；
  **`.git/` 里的事件被忽略**（那是仓库在写自己，不是工作树变了）。
- **`isCurrent(entry, since, options)`**：只有「客户端拿着同一份 revision」
  「工作树没变」「选项相同」「快照还没过期」四条都成立，宿主才回答「没变」。
- **兜底**：快照最多活 `STATUS_FALLBACK_MS = 15 000` ms；**即使 watcher 漏了事件**，
  下一��请求也会重新取一次快照。漏事件的代价是「状态最多旧 15 秒」，
  而不是「状态永远停在旧值」。 [读码确认]
- **闲置回收**：90 秒没有请求的仓库会关掉自己的 watcher（`STATUS_WATCH_IDLE_MS`）；
  插件 teardown 时 `statusCache.clear()` 关掉全部。**不留悬挂的句柄。**

### 3.2 宿主路由：`src/index.js` 的 `git.status`

```js
const entry = statusCache.entry(payload?.root ?? '')
if (statusCache.isCurrent(entry, payload?.since, options)) {
  return { unchanged: true, revision: entry.revision }   // ← 不跑 git，不发快照
}
```

- 回答带 `revision`（宿主进程内**全局唯一**的计数），客户端把它带回来。
- **不带 `since` 的请求（显式刷新：stage / commit / 切窗口 / 页面回到前台）永远拿新快照**，
  所以「显式刷新要的是此刻的状态」这条语义没有变。
- 老客户端不传 `since` → 宿主行为与改动前**完全一致**（向前兼容）。

### 3.3 客户端：`src/client/store.js` 的轮询段

- **后台轮询**才带 `since`；显式刷新不带。
- 宿主回答 `unchanged: true` 时，客户端**什么都不写**：
  状态对象不动、`statusAt` 不动、订阅者不被唤醒 → **整个工作台不再每 2 秒重建一次**。
- revision 存在 store 的实例字段上（`this.statusRevision`），**不进 state** ——
  这正是「一次没变的轮询不写任何东西」的关键。

### 3.4 客户端：`src/client/css-scope.js`（新增）+ `src/client/index.jsx`

宿主自己也有 CodeMirror（它的聊天输入就是，`app.asar` 里能搜到 `cm-foldGutter`）。
工作台样式表里有 **4 条规则直接写着 `.cm-foldGutter` / `.cm-foldPlaceholder`** ——
它们会命中宿主的编辑器。 [实测确认]

这 4 条规则现在被绑到 `:where(.iwb-root)` 下：**作用域在、样式不变**（`:where()` 不计权重，
特异性与改动前一致），但它们**再也够不到宿主的 DOM**。

> 规范上更干净的做法是把作用域直接写进 `src/client/styles.js`（那 4 条规则各加一个前缀）。
> 本轮没有改那个文件（它在别的改动者的范围内），改法见 §5。

## 4. 闸门

| 文件 | 闸门 | 没有修复时会红的原因 |
|---|---|---|
| `tests/perf-status-refresh.test.mjs` | 「the poll of an unchanged work tree does not run git at all」 | 修复前第二次轮询会再跑一次 git，`gitProcessCount()` 会变 |
| 同上 | 「a snapshot that nothing changed stays the snapshot of the client」 | 没有 revision 机制，`isCurrent` 不存在 |
| 同上 | 「a change in the work tree makes the snapshot stale」 | 没有 watcher，宿主不知道工作树变了 |
| 同上 | 「a change the watcher missed is caught by the fallback」 | 没有兜底，漏事件 = 状态永远停在旧值 |
| 同上 | 「the repository writing into itself is not a change of the work tree」 | 没有 `.git` 过滤 → 快照把自己的仓库当成变了 → 无限刷新 |
| 同上 | 「a change that happens while the snapshot is taken is not swallowed」 | 用布尔标志会吞掉取快照期间到达的变化 |
| 同上 | 「a watch that cannot be established keeps the status correct」 | watch 失败时必须退回「每次都取」 |
| 同上 | 「a work tree that nobody asks for any more releases its watch」 | watcher 会永远挂在宿主进程里 |
| 同上 | 「the teardown of the plugin closes every watch」 | 同上 |
| `tests/perf-status-poll.test.mjs` | 「a poll that finds nothing changed writes nothing」 | 修复前每次轮询都写 `statusAt` → 状态对象换新 → 订阅者被唤醒 → 整个工作台重建 |
| 同上 | 「the background poll names the revision it holds」 | 没有 `since`，宿主无从判断 |
| 同上 | 「an explicit refresh asks for a new snapshot」 | 显式刷新若也带 `since`，会拿到过期状态 |
| `tests/perf-host-containment.test.mjs` | 「no rule of the workbench reaches the CodeMirror of the host」 | 4 条 `.cm-` 规则没有作用域 |
| 同上 | 「the fold gutter of the workbench keeps its own theme」 | 作用域加错会让工作台自己的折叠标记失去主题 |
| 同上 | 「the scope of the workbench is the editor of the workbench」 | 作用域指向一个不存在的类 → 工作台丢样式 |

**全部与机器快慢无关**：没有一处断言依赖挂钟；watch 用假的驱动，
路由的集成闸门数的是 **git 子进程数**，不是毫秒。

**验证方式**：新增闸门在修复前会红（`isCurrent` / `unchanged` / `since` 这些符号当时根本不存在），
修复后全绿；已有的 889 条用例（含 `perf-hot-path` / `perf-notify` / `perf-slice-*`）
**一个都没有被放宽**。

## 6. 没有做到的（明说）

1. **没有端到端的真机 CPU 采样**：DSH 的 web 端在重启后要求带认证的 URL，
   这一轮拿不到已登录的页面，所以「宿主进程的 CPU 曲线」是**推断 + 组件级实测**，
   不是端到端采样。组件级实测是硬的（子进程数、响应体大小、解析毫秒）。
2. **没有在 Linux 上验证递归 watch**：Node 18 没有递归 watch；
   Node ≥ 20.13 有，但 inotify 的 watch 数有上限（`fs.inotify.max_user_watches`），
   一个几十万目录的仓库可能 `ENOSPC`。**代码路径有兜底**（watch 建不起来 → 退回「每次都取」），
   但**上限本身没有测过**。
3. **查找路径（`git grep`）没有改**：一次搜索在 1.5 万文件的仓库里约 **2.4 s**，
   是宿主进程里的 CPU 尖峰。`src/host/search.js` / `src/host/scanner.js` 在本轮的范围外，
   改法另议。
4. **没有改 `src/host/git.js` 的 `status()`**：它的一次快照仍然是 1（或 3）个子进程，
   `MAX_STATUS_ENTRIES` 仍然是 20 000，**响应体仍然可能有 2.41 MiB**。
   本轮把它藏到了「只有工作树真的变了才发」的后面；
   要彻底解决（大仓库的快照体积），得给快照本身一个上限或一个差量协议。
