feat(v6): split the workbench into core and codeintel

The plugin had grown heavy because it carried the code intelligence inside
itself, and that made it unstable to use. This commit splits it along the
commit boundary the PRD pinned: the IDE workbench becomes a clean baseline,
the code intelligence becomes a plugin of its own.

The repository becomes a monorepo with three packages:

  packages/contract   the contract between the two (private, not published)
  packages/workbench  the core - plugin ID dsh-ide-workbench, UNCHANGED
  packages/codeintel  the code intelligence - plugin ID dsh-ide-codeintel

The core keeps the four tool windows, the editor, the file locator and the
repository picker. It carries NO language server, NO completion and no memory
budget - but it keeps the automatic closing of the brackets, which is a
general editing ability, not code intelligence.

The contract is the only way between the two:

  host side   a Cordis service (dsh-ide-workbench.contract), taken SOFTLY -
              a hard inject would keep the codeintel from ever applying when
              the core is missing, and the user would see no guidance at all
  client side four slots (editor bridge, status item, settings group, editor
              command); the contract travels as a prop, so there is no global
              variable and no namespace pollution
  editor      a seam: extension slots, key bindings, commands, the open
              document and the reveal

Three findings shaped the implementation:

1. The CodeMirror runtime has to be ONE. Two copies of @codemirror/state in
   the page break every instanceof check of the editor - CodeMirror says so
   itself. The core therefore owns the runtime and hands it over; the
   codeintel reaches it through a lazy proxy. The proxy is an ES module with
   one named lazy proxy per export: a CommonJS proxy (as sketched in the
   PRD) loses every named import, because esbuild copies only the keys a
   proxy can enumerate. @codemirror/lsp-client is loaded DYNAMICALLY - a
   static import runs its module body while the bundle loads, and that body
   touches the aliased @codemirror/state, which would make the plugin
   impossible to install on its own.

2. The automatic closing of the brackets lives on both sides, and the core
   gives way. The extension slots are merged by key and priority: the loser
   is NOT installed at all, and the winner does not depend on the order the
   plugins were loaded in.

3. A fault belongs to the plugin whose sources it points at. The
   attribution lives in a registry shared through Symbol.for, and the
   process has exactly ONE uncaughtException handler - so a fault of the
   codeintel can no longer kill the DSH host, and it can no longer be handed
   on twice.

Verified: 412 core tests, 814 codeintel tests, 26 contract tests, and 15
mechanical checks - among them the artifact-level proof that the codeintel
bundle contains NO copy of CodeMirror, and that it loads in a bare sandbox
without the runtime (so it can be installed alone).
